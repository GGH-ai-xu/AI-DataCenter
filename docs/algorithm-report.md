## 一、功耗预测算法

平台采用 **三算法竞争择优** 策略预测未来 24 小时逐小时功耗，确保在不同数据质量和负载模式下均能给出最优预测。

### 1.1 指数加权平均（EWA）

**文件**: `backend/app/services/energy_analytics.py:286-298`

**公式**:

$$\hat{P} = \frac{\sum_{j=0}^{n-1} w_j \cdot P_j}{\sum_{j=0}^{n-1} w_j}, \quad w_j = e^{-\alpha \cdot (n-1-j)}$$

其中 α = 0.3 为衰减常数，$P_j$ 为第 j 个历史观测值。

**α = 0.3 的选择依据**:

- GPU 功耗时序具有明显的日周期性（高峰/低谷/平峰），但同时受到任务提交的随机性影响。
- α 过小（如 0.1）会过度平滑，无法捕捉近期负载变化；α 过大（如 0.7）则对噪声过于敏感。
- 在 α = 0.3 下，最近 1 小时的观测权重约为最近 3 小时的 1.8 倍（$e^{0.3 \times 2} \approx 1.82$），既保留了近期趋势的响应性，又不会被单个异常值主导。
- 这一取值在指数平滑文献中属于"中等响应速度"区间，适合小时级预测粒度。

**标准差计算**: 采用加权方差的平方根，用于构建预测置信区间：

$$\sigma = \sqrt{\frac{\sum w_j \cdot (P_j - \hat{P})^2}{\sum w_j}}$$

**优势**: 无外部依赖（纯 Python math 库），任意数量数据点均可计算，作为 numpy 不可用时的保底算法。

### 1.2 线性回归预测

**文件**: `backend/app/services/energy_analytics.py:300-315`

**模型**: $P(t) = a \cdot t + b$，使用 numpy.polyfit(x, y, 1) 拟合。

**最少数据要求**: 3 个历史数据点。

**适用场景**: 当功耗呈单调上升或下降趋势时（如逐步增加训练任务阶段），线性模型能准确捕捉趋势方向并外推。

**精度指标**:
- RMSE（均方根误差）：衡量预测值与真实值的偏差
- R²（决定系数）：衡量模型对数据变异的解释比例，R² = 1 - SS_res/SS_tot

### 1.3 二次多项式拟合

**文件**: `backend/app/services/energy_analytics.py:317-336`

**模型**: $P(t) = a \cdot t^2 + b \cdot t + c$，使用 numpy.polyfit(x, y, 2) 拟合。

**最少数据要求**: 5 个历史数据点。

**degree = 2 的选择依据**:

- degree = 1（线性）对 GPU 负载的日内曲线（凸起-下降模式）拟合能力不足。
- degree = 2（二次）能捕捉功耗的单峰/单谷模式（如上午逐步升高、午间达峰、下午回落）。
- degree ≥ 3 在外推时极易发散（高次多项式的端点行为不稳定），对于 24 小时预测来说风险过高。

**反发散保护机制**（lines 326-327）:

```python
if predicted < 0 or predicted > max_val * 3:
    return None  # 弃用该预测
```

- 功耗不可能为负值（物理约束）。
- 预测值超过历史最大值的 3 倍说明多项式在外推区域已发散，此时放弃该模型，回退到 EWA 或线性。
- 3 倍阈值是经验值，在 RTX 3090 场景下（TDP 350W），即使异常突增也不会超过 1050W。

### 1.4 自动择优机制

**文件**: `backend/app/services/energy_analytics.py:338-426`

**竞选流程（逐小时执行）**:

1. 收集目标小时的 7 天历史数据（同一小时段的历史功耗值）
2. 三种算法各自运行，返回 (predicted, std, rmse, r_squared)
3. **以 RMSE 为评判标准**，选择 RMSE 最低的算法作为该小时的预测结果
4. EWA 作为兜底（始终可用），其 RMSE 近似为标准差

**选择 RMSE 而非 R² 的理由**:

- RMSE 具有与原始数据相同的量纲（W），物理含义直观。
- R² 在数据方差极小时（如稳定负载下方差接近 0）可能产生误导性极端值。
- RMSE 对所有算法一视同仁，不偏袒某种模型复杂度。

**统计输出**: 每次预测记录各算法的命中次数（ewa_count, linear_count, polynomial_count），支持后续分析数据特性。

## 二、公平治理评分算法

### 2.1 用户公平性评分（User Fairness Score）

**文件**: `backend/app/services/governance.py:338-354`

**核心公式**:

```
fairness_score = max(0, 100
    - share_overuse × 1.5    # 显存份额超用惩罚
    - power_overuse × 1.1    # 功率份额超用惩罚
    - task_overuse  × 0.8    # 任务数份额超用惩罚
    - runtime_penalty         # 长时间运行惩罚
    - deferrable_penalty      # 可延迟任务惩罚
    + urgent_credit           # 紧急任务加分
)
```

**权重设计理由**:

| 因子 | 权重 | 设计依据 |
|------|------|----------|
| share_overuse × **1.5** | 最高 | 显存是 GPU 最稀缺资源，分配后运行时不可回收，超占影响最大 |
| power_overuse × **1.1** | 次高 | 功率影响电费和散热，但可通过 power limit 动态调整 |
| task_overuse × **0.8** | 较低 | 任务数多不等于资源占用高（如多个小任务），且任务可暂停/终止，恢复性最强 |

**运行时间惩罚**（lines 341）:

```python
runtime_penalty = min(18.0, runtime_hours × factor)
factor = 0.9 if urgent_count > 0 else 1.2
```

- 长时间占用 GPU 的用户应受到递增惩罚，鼓励资源轮换。
- 上限 18 分：避免对确实需要长时间训练的用户过度惩罚。
- 紧急任务用户使用 0.9 系数（较宽容）：紧急任务本身就需要更长的不间断运行。
- 普通用户使用 1.2 系数（较严格）：没有紧急需求的长时间占用更应被约束。

**可延迟任务惩罚**（line 342）:

```python
deferrable_penalty = deferrable_count × (4.0 if share_overuse > 0 else 2.0)
```

- 可延迟任务本身就表示该任务"不急"，在资源紧张时应优先让路。
- **超额放大**：当用户已经超出公平份额时（share_overuse > 0），持有可延迟任务的惩罚翻倍（4.0 vs 2.0），因为"既超占又不急"是最不合理的状态。

**紧急任务加分**（line 343）:

```python
urgent_credit = min(15.0, urgent_count × 5.0)
```

- 上限 15 分，最多抵消 3 个紧急任务的加分。
- 紧急任务代表用户有合理的高优先级需求，但不应无限制累加。

**评分等级**:

| 分数范围 | 等级 | 建议动作 |
|----------|------|----------|
| ≥ 80 | balanced（均衡） | 维持现状 |
| 60–80 | watch（关注） | 限制新增可延迟任务 |
| < 60 | dominant（主导） | 优先收缩可延迟任务 |

### 2.2 系统公平治理指数（System Fairness Index）

**文件**: `backend/app/services/governance.py:420-471`

**分布差距计算**:

```python
def _distribution_gap(values, ideal_share_pct):
    return sum(abs(value - ideal_share_pct) for value in values) / 200
```

除以 200 是归一化设计：在最极端情况下（1 个用户占 100%、其余用户占 0%），偏差总和最大约为 200%（占用者偏差 + 所有其他用户偏差之和），此时 gap 归一化到 1.0。

**系统指数公式**:

```
fairness_index = max(0, 100
    - memory_gap × 35
    - power_gap  × 25
    - task_gap   × 35
    - max(0, highest_share_pct - ideal_share_pct) × 0.55
)
```

**权重 35/25/35 的设计依据**:

- 显存(35) + 任务(35) = 70：这两个维度代表"资源占用的广度和深度"。
- 功率(25)：功率虽影响电费，但可动态调节，不如显存和任务数那样直接反映公平性。
- 单一用户集中度惩罚（0.55）：当某个用户的有效份额远超理想份额时，额外扣分，确保即使整体分布看似均匀但有极端个体时也能检出。

**系统等级**:

| 指数范围 | 等级 | 含义 |
|----------|------|------|
| ≥ 85 | balanced | 资源分配均衡 |
| 65–85 | watch | 开始向少数用户集中 |
| < 65 | critical | 资源集中度偏高，需干预 |

### 2.3 让路候选评分（Yield Candidate Score）

**文件**: `backend/app/services/governance.py:577-586`

**评分公式**:

```
yield_score = priority_score + share_score + memory_score + runtime_score + quota_score
```

| 因子 | 计算 | 范围 | 权重设计 |
|------|------|------|----------|
| priority_score | deferrable=100, normal=55, urgent=0 | 0–100 | 可延迟任务是最佳让路对象，分值几乎是 normal 的 2 倍 |
| share_score | share_overuse_pct × 2.2 | 0–∞ | 用户超占越多，其任务越应优先让路 |
| memory_score | min(30, gpu_memory_gb × 4.0) | 0–30 | 大内存任务释放后效果显著，封顶 30 防止单因子主导 |
| runtime_score | min(20, runtime_hours) | 0–20 | 运行越久越应考虑轮换，封顶 20 |
| quota_score | violation_count × 28.0 | 0–∞ | 违规用户的任务获得强烈的让路信号，28 分≈1 个可延迟任务的优先级分 |

**过滤规则**:
- 紧急任务永不让路
- 用户和系统均为均衡状态时不产生候选
- 受保护用户（allow_preempt=False）排除

## 三、GPU 效率评分算法

**文件**: `backend/app/services/energy_analytics.py:183-195, 260-268`

**公式**:

```
power_ratio = power_usage / power_limit
score = min(100, gpu_utilization / max(power_ratio, 0.01))
```

**设计思路**:
- 效率 = 计算利用率 / 功耗消费比。
- 高利用率 + 低功耗比 = 高效率（满载且不浪费电）。
- 低利用率 + 高功耗比 = 低效率（空转但耗电大）。
- 下限 0.01 防止除零。

**温度惩罚**:

| 温度 | 惩罚系数 | 理由 |
|------|----------|------|
| ≥ 85°C | × 0.8 | GPU 进入热保护区间，触发硬件降频，实际有效计算能力下降 |
| ≥ 75°C | × 0.9 | 接近热保护阈值，长期运行会导致频率波动和寿命缩短 |
| < 75°C | × 1.0 | 正常工作温度，无惩罚 |

## 四、预算调度算法

### 4.1 功率预算执行策略

**文件**: `backend/app/services/scheduler.py:256-354`

**两阶段策略**:

**阶段一：功率限制（优先使用，影响最小）**

按优先级由低到高排序 GPU，依次建议降低功率上限：

| 最低优先级 | 功率下限 | 压缩比 | 设计逻辑 |
|-----------|----------|--------|----------|
| deferrable | 150W | 0.72–0.80 | 可延迟任务可承受较大降频，保留核心计算即可 |
| normal | 180W | 0.82–0.88 | 普通任务需要适度性能保障 |
| urgent | 220W | 0.90–0.94 | 紧急任务只做轻微降频，且高利用率时跳过 |

- 压缩比根据利用率分段：低利用率时使用更激进的压缩（因为实际消耗本就低于上限）。
- 功率下限确保 GPU 不会被限制到无法完成基本计算的水平。
- 紧急 + 高利用率（≥85%）的 GPU 完全跳过。

**阶段二：暂停任务（仅当阶段一不足时）**

仅当降功率后总功耗仍超预算时启动：
- 候选范围：优先级低于 urgent 的所有任务。
- 排序规则：优先级 → 利用率 → 功耗（从低到高）。
- 预估节能：deferrable 任务 max(40W, power×0.35)，其他 max(25W, power×0.2)。

**恢复机制**（lines 234-254）:

当总功率 < 预算 - 恢复余量（预算的 8%）时，逐步恢复之前被压缩的 GPU 到原始功率上限。

### 4.2 碳预算追踪

**文件**: `backend/app/services/scheduler.py:91-147`

**累积计算**: 每次 tick（2 秒间隔）累加当前总功率对应的能耗：

```python
_carbon_accumulated_wh += total_power_w × (2.0 / 3600)  # Wh
```

**碳排放转换**:

```
accumulated_kwh = accumulated_wh / 1000
accumulated_carbon_kg = accumulated_kwh × 0.5703
```

**碳排放因子 0.5703 kgCO₂/kWh 来源**: 中国国家电网 2023 年度排放因子，由生态环境部《全国电网平均排放因子》公布。该值代表消耗 1 度电对应的 CO₂ 排放量。

**日投影**: 基于已运行时段的平均能耗速率，线性外推至 24 小时。

**午夜重置**: 检查当前时间是否跨过当日 00:00，是则清零累积值。

## 五、规则引擎

**文件**: `backend/app/services/scheduler.py:375-400`

当前实现两条硬性温度规则，**无条件立即执行**:

| 规则 | 条件 | 动作 | 优先级 |
|------|------|------|--------|
| emergency_thermal | 温度 ≥ 90°C | 设置功率上限 200W | 最高（紧急保护） |
| thermal_warning | 温度 ≥ 85°C | 设置功率上限 250W | 高（预防性降频） |

**设计决策**:
- 85°C 是 NVIDIA GPU 开始触发硬件热保护的典型阈值。
- 90°C 接近多数 GPU 的最大工作温度（RTX 3090 Tjunction 最高 93°C），必须紧急干预。
- 规则引擎在每次 tick 中**最先**执行，确保安全优先于性能优化。

## 六、规则优化建议生成算法

**文件**: `backend/app/services/energy_analytics.py:527-618`

当 LLM 不可用时，系统降级为规则驱动的优化建议。五条规则按优先级判定：

| 规则 | 触发条件 | 目标功率 | 设计逻辑 |
|------|----------|----------|----------|
| 低利用高功耗 | util<30% & power>40%limit | max(150, power×0.55) | 显著功耗浪费，保留基本运行功率即可 |
| 功耗效率不匹配 | power>50%limit & util<80%×power_ratio | max(180, util/100×limit×1.2) | 按实际利用率匹配功率，预留 20% 余量 |
| 高峰期非满载 | 高峰时段 & util<80% | max(200, limit×0.7) | 电价高峰削峰，非满载时降 30% |
| 低谷期低负载 | 低谷时段 & util<40% | max(150, power×0.6) | 低谷适合低功耗运行 |
| 高温保护 | temp≥75°C | max(200, limit×0.7) | 降频保护硬件寿命 |

**去重策略**: 同一 GPU 只保留预估节能最大的建议，防止重复调整。

## 七、LLM 混合调度策略

**文件**: `backend/app/services/scheduler.py:525-568`

**tick 执行序列**:

```
1. 碳预算累积（每次 tick）
2. 评估上次 AI 调度效果（如果有 LLM + 上次动作）
3. 规则引擎 → 立即执行
4. 预算调度 → 立即执行
5. AI 调度 → 每 5 分钟执行一次（间隔控制）
```

**分层设计理由**:

- **规则引擎**（硬规则）：安全兜底，不依赖 LLM，响应时间 < 100ms。
- **预算调度**（算法规则）：基于确定性算法，可预测、可回滚。
- **AI 调度**（LLM 生成）：更灵活的策略，但有延迟和不确定性，因此间隔 5 分钟并在前两层之后执行。

**闭环反馈**（D4 特性）: 每次 AI 调度前，先评估上次调度的效果（before/after 对比），评估结果记入调度日志，为下次调度提供改进依据。
