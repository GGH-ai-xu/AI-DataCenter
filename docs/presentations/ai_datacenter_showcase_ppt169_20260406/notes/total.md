# slide_01_cover

这页先把项目定位立住。我们的目标不是做一个只会展示 GPU 数据的面板，而是打造智算中心优化代码生成系统。[停顿] 后面所有页面都围绕登录、导入、范围和治理这四个关键词展开。

要点：① 项目是智算中心优化代码生成系统而非监控看板 ② 共享算力场景是主要应用背景 ③ 后续内容围绕闭环能力展开
时长：0.8 分钟

---

# slide_02_definition

[过渡] 在进入细节之前，先回答一个最核心的问题：我们到底做的是什么。AI DataCenter 把平台身份、导入边界和控制台治理组织成了一条完整主线，因此它首先是平台而不是单页工具。

要点：① 一句话项目定义 ② 登录、导入、控制台职责分离 ③ 平台化是核心差异
时长：0.8 分钟

---

# slide_03_background

[过渡] 为什么会需要这样一套平台？因为共享 GPU 已经不是少数人的场景。多角色、多机器、多任务同时出现之后，管理成本不再是线性的。

要点：① 共享 GPU 场景普及 ② 三类结构性矛盾 ③ 看得到资源不等于能治理资源
时长：0.9 分钟

---

# slide_04_pain_points

[过渡] 如果沿用传统 SSH、脚本和零散监控页，平台会把复杂性转移给人。[停顿] 入口分散、边界模糊、安全薄弱和复盘困难，是当前方式最集中的四个问题。

要点：① 四类典型痛点 ② 传统方式治理阻力高 ③ 问题集中在边界和协同
时长：0.9 分钟

---

# slide_05_solution

[过渡] 因此我们的方案不是给旧流程再贴一层 UI，而是重构整条治理路径。登录、导入、选卡和控制台分别承担不同职责，系统边界随之变得稳定。

要点：① 四步闭环 ② 身份先于连接 ③ 范围先于动作
时长：0.8 分钟

---

# slide_06_personas

[过渡] 这套平台面向的不是单一用户，而是多类角色共同使用的治理底座。管理员、负责人、工程师和展示者都可以在同一个系统里获得自己的工作视角。

要点：① 四类核心角色 ② 同一平台服务不同目标 ③ 产品表达兼顾使用和展示
时长：0.8 分钟

---

# slide_07_flow

[过渡] 接下来我们看用户真正的使用路径。平台把复杂的接入过程拆成六个稳定步骤，因此用户不会在控制台里临时切换连接和范围。

要点：① 六步主流程 ② 导入层在控制台之前 ③ 使用路径可预测
时长：0.9 分钟

---

# slide_08_login

[过渡] 首先是登录入口。平台用户身份必须先建立，因为已保存主机、凭据复用和可见范围都依赖这层身份边界。

要点：① 先登录再导入 ② 默认管理员与首登改密 ③ 管理员和普通用户范围不同
时长：0.9 分钟

---

# slide_09_import_workspace

[过渡] 登录之后并不是直接进入控制台，而是先进入准备页。[停顿] 这一步把接入逻辑和治理逻辑完全剥离，是产品结构上的关键变化。

要点：① 独立准备页 ② 四个稳定阶段 ③ 控制台不再承担接入切换
时长：0.9 分钟

---

# slide_10_access_modes

[过渡] 在准备页里，平台支持三种接入方式：本机 Agent、远程 Agent 和 SSH Linux。它们适用于不同部署环境，但最终在前端都被收敛成同一套导入语义。

要点：① 三种接入方式 ② 部署环境覆盖更广 ③ 前端语义保持统一
时长：0.9 分钟

---

# slide_11_scan_select

[过渡] 一旦接入成功，用户首先看到的是真实硬件状态，而不是直接进入管理页。CPU、GPU、利用率和当前卡状态都会先被确认，然后再选择导入范围。

要点：① 扫描先于导入 ② 入台前确认 CPU/GPU 状态 ③ 用户主动选择治理范围
时长：0.9 分钟

---

# slide_12_scope_control

[过渡] 这是整套系统最关键的产品边界。控制台只显示和治理本次导入选中的卡，因此误操作和信息噪声都会明显下降。

要点：① 本次导入范围收束 ② 控制台不混入无关 GPU ③ 责任边界更加清晰
时长：1.0 分钟

---

# slide_13_saved_hosts

[过渡] 如果用户已经连接过某台机器，平台会把它保存成可复用的主机记录。下次登录时，用户可以直接扫描并继续，而不是重新输入所有 SSH 信息。

要点：① 已保存主机入口 ② 扫描并继续 ③ 凭据失效时显式恢复
时长：0.9 分钟

---

# slide_14_console

[过渡] 完成导入后，控制台才真正开始发挥作用。它只保留治理相关能力，不再混入连接选择和接入切换逻辑。

要点：① 控制台专注治理 ② 模块入口清晰 ③ 工作区围绕导入范围展开
时长：0.8 分钟

---

# slide_15_governance_loop

[过渡] 监控与治理是一体的，这也是平台化价值所在。用户可以从状态观察直接走到治理动作，再回到结果观察，形成闭环。

要点：① 监控与治理联动 ② 支持真实动作 ③ 结果可即时回流
时长：0.9 分钟

---

# slide_16_operations_layer

[过渡] 当底层治理能力成立之后，平台自然会进入运营层。[停顿] 告警中心、任务管理和调度能力让系统从“能用”走向“能运营”。

要点：① 告警任务调度三工作台 ② 平台从监控走向运营 ③ 适合长期使用场景
时长：0.8 分钟

---

# slide_17_desktop_delivery

[过渡] 为了适应本地演示和内网交付场景，平台还提供了 Electron 桌面壳。它把前端、后端和 agent 的启动关系打包成更完整的交付形态。

要点：① 桌面壳交付 ② 本地运行脚本 ③ 适合 Windows 与内网环境
时长：0.8 分钟

# slide_18_architecture

[过渡] 下面进入技术实现部分。整体上，系统采用展示层、平台层、接入层和目标与存储层四层结构，这让产品边界和工程边界保持一致。

要点：① 四层架构 ② 前端后端 provider 分层 ③ 有利于扩展和维护
时长：1.0 分钟

---

# slide_19_runtime_scope

[过渡] 导入层不仅是界面入口，也是运行时状态入口。import context 会把 provider 类型和导入 GPU 索引固定下来，后续控制台只消费过滤后的数据。

要点：① import context 是核心状态 ② provider_type 与 GPU 索引被持久化 ③ 控制台基于范围过滤数据
时长：1.0 分钟

---

# slide_20_dual_provider

[过渡] 平台之所以能够同时兼容部署 Agent 和不部署 Agent 的机器，是因为内部做了 provider 抽象。Agent 和 SSH Linux 两条链路都被纳入统一运行时模型。

要点：① 双 provider 架构 ② Agent 与 SSH 模式并行 ③ 对外保持同一产品流程
时长：1.0 分钟

---

# slide_21_auth_boundary

[过渡] 在安全设计上，平台登录和 SSH 认证被严格拆成两条链路。平台身份决定 API 可见范围，SSH 凭据只负责连接目标主机。

要点：① 两条认证链路 ② 平台身份与 SSH 解耦 ③ 角色可见范围明确
时长：0.9 分钟

---

# slide_22_credential_security

[过渡] 进一步地，用户输入的 SSH 密码、私钥和 sudo 密码不会被明文保存。主密钥负责加密和解密复用，而且一旦失效就显式报错。

要点：① 主密钥加密机制 ② 凭据可复用但不明文落盘 ③ 坚持显式失败原则
时长：1.0 分钟

---

# slide_23_engineering

[过渡] 除了功能本身，工程化链路也决定了项目是否真的可交付。start-dev、install-deps、测试和桌面壳共同提高了系统的稳定性与展示完成度。

要点：① 启动与依赖脚本 ② 前后端测试与构建 ③ 从 demo 走向可交付系统
时长：0.9 分钟
