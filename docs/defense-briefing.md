## 1. 项目定位与核心卖点

### 一句话定位

> **智算中心优化代码生成系统** —— 不只是"把数据画出来"，而是真实采集、真实治理、真实复盘的完整软件系统。

### 解决什么问题

实验室里 4 张 RTX 3090 多人共用，经常出现：
- 某个人的训练跑满了所有显存，别人排不上队
- 没人管功耗，电费超标、GPU 过热
- 出了问题不知道是谁的进程、跑了多久、用了多少资源
- 想调度任务，但不敢动，怕搞坏别人的训练

我们做的就是**把这些"人治"变成"系统治"**。

### 五大核心卖点（和普通监控面板的区别）

| # | 卖点 | 一句话解释 |
|---|------|-----------|
| 1 | **真实治理，不只是看** | 可以暂停、恢复、终止进程，可以设置功耗上限，不是只看个图表 |
| 2 | **演练模式 + 风险确认** | 所有危险操作先演练预览，确认后才真实执行，杜绝误操作 |
| 3 | **公平性量化** | 用 6 个维度给每个用户打分，不是凭感觉说"你占多了" |
| 4 | **三种算法自动比赛** | 功耗预测不依赖单一模型，三种算法每小时比 RMSE，自动选最准的 |
| 5 | **碳排放追踪** | 每度电转化成碳排放，用国网官方数据，让节能看得见 |

### 30 秒电梯演说（答辩开场可直接用）

> "我们做的是一个智算中心优化代码生成系统。实验室里多人共用 GPU，经常有人占满资源、功耗超标、任务冲突。现有工具只能看，不能管。我们的系统从底层采集真实 GPU 数据，自动检测异常和不公平，支持暂停、限功率、调优先级等治理操作，还有演练模式防止误操作。内置三种预测算法自动选优、六维度公平性评分、碳排放追踪。213 项自动化测试全部通过，支持 Web 和 Windows 桌面两种部署方式。"

### 2.1 治理总览（Dashboard）

**做什么用的**：新用户进来第一个看到的页面。接上数据源、跑一次自检、看全局状态，然后决定该去哪个台处理问题。

**三个标签页**：
- **概览**：治理判断大卡（"立即执行 / 建议干预 / 继续观测"）、关键指标（活跃用户、紧急任务、严重告警）、快速跳转入口（治理台、处置台、风险台、复盘台）、**数据统计卡**（历史数据总量、采集时长、吞吐率）
- **接入与自检**：选择"本机模式"或"远程服务器模式"连接 Agent、9 项链路自检、桌面版服务管理
- **实时态势**：GPU 网格实时状态、功率趋势图、最新告警

**📸 PPT 截图建议**：
- 概览页的治理判断大卡 + 下方快速入口（展示"不只是看数据，而是引导治理决策"）
- 自检结果页（展示系统完整性验证）
- 数据统计卡（展示"大数据采集规模"）

**🎤 演示时说**：
> "进入系统，首先看到治理判断——系统自动分析当前状态，告诉你该不该干预。下面是快速入口，直达对应的治理台。右下角是数据统计，可以看到平台已经采集了多少条数据。"

### 2.2 任务治理（TaskManager）

**做什么用的**：这是"动手"的地方。看到所有 GPU 进程，决定哪些暂停、哪些终止、哪些调优先级。

**三个标签页**：
- **待处置任务**：搜索过滤 → 任务账本（每个进程一张卡片，显示 PID、用户、显存、CPU、优先级、操作按钮）→ 执行模式切换（演练/真实）→ 让路候选任务
- **公平治理**：公平指数仪表盘（0-100 分圆环图）、用户资源占比柱状图、治理建议、让路候选任务
- **规则配置**：为每个用户设置角色（保护/普通/受限）、最多任务数、最多 GPU 数、显存额度、是否允许让路

**📸 PPT 截图建议**：
- 任务账本的进程卡片（展示"可以看到每个进程的详细信息和操作按钮"）
- 公平指数仪表盘（展示"公平性量化"）
- 规则配置面板（展示"精细化管理"）

**🎤 演示时说**：
> "每个 GPU 进程都有独立的卡片，显示是谁的、用了多少显存、能不能治理。演练模式下点暂停，系统会告诉你'如果真实执行会发生什么'，但不会真的动。切到公平治理标签，可以看到公平指数——100 分是完全公平，低于 60 分说明资源集中度过高。"

### 2.3 预算与调度（Scheduler）

**做什么用的**：设定"这个实验室最多用多少电"，系统自动帮你控制。

**三个标签页**：
- **治理控制**：总功率预算设置（如 1200W）+ 开关、碳预算设置（如每天 15kg CO₂）+ 开关、自动调度开关、手动功耗控制（每张卡一个滑块，100-350W）、执行模式切换
- **执行结果**：调度报告、三种策略效果对比（规则引擎 vs 预算引擎 vs AI 调度）、AI 调度效果评估（PDCA 闭环）
- **审计台账**：所有治理操作的日志记录（时间、动作、目标、原因、结果）

**📸 PPT 截图建议**：
- 总功率预算的进度条（当前功率 vs 预算上限）
- 手动功耗控制面板（每张卡一个滑块）
- 三策略对比卡片（展示"多策略混合调度"）

**🎤 演示时说**：
> "这里可以设定整个实验室的功率预算。假设预算是 1200W，当 4 张卡加起来超了，系统会自动按优先级降低功率——先压不急的任务，最后才动紧急任务。右边可以看到三种策略各自建议了什么动作。"

### 2.4 能耗治理（EnergyOptimization）

**做什么用的**：看能耗数据、做预测、算碳排放、一键优化。这是"复盘台"。

**五个标签页**：

- **预测与对比**：未来 24h 功耗预测图（含置信区间）、效率评分横向柱图、调度历史回放
- **AI 洞察**：AI 趋势分析、异常模式检测

## 3. 技术架构（简化版）

### 三个组成部分

用一个类比来理解：

```
┌──────────────┐     采集+执行      ┌──────────────┐     展示+交互     ┌──────────────┐
│  Agent       │ ◄──────────────► │   Backend    │ ◄──────────────► │   Frontend   │
│  (前线哨兵)  │     HTTP 请求     │  (指挥中心)  │   REST + WS      │  (作战屏幕)  │
│  部署在GPU机 │                   │  部署在后端机 │                  │  浏览器里跑  │
└──────────────┘                   └──────────────┘                  └──────────────┘
```

- **Agent（前线哨兵）**：装在有 GPU 的电脑上。每秒读取 GPU 温度、功耗、显存、进程列表。也能执行命令：设功耗上限、暂停/终止进程。
- **Backend（指挥中心）**：每 2 秒从 Agent 拉数据，存到数据库，跑告警检测、调度引擎、公平性分析、能耗预测。对外提供 50+ 个 API 接口。
- **Frontend（作战屏幕）**：8 个页面的 Web 界面，通过 WebSocket 实时更新数据，用户在这里看和操作。

### 数据怎么流动

```
GPU 硬件 → Agent 采集（2秒）→ Backend 存库 → 告警检测 → 调度引擎 → WebSocket 推送 → 前端实时刷新
                                                                      ↓
                                                              碳核算 / 公平评分 / 能耗预测
```

**关键数据链路**：
1. **实时链路**（2 秒一次）：Agent 采集 → Backend 存储 → WebSocket → 前端更新
2. **治理链路**（自动/手动）：规则引擎 → 功率预算 → AI 调度 → Agent 执行 → 审计记录
3. **分析链路**（按需）：历史数据 → 预测/评分/碳计算 → API 返回 → 前端可视化

### 技术选型与理由（答辩可能被问到）

| 技术 | 选择 | 为什么 |
|------|------|--------|
| 前端框架 | Vue 3 | 组合式 API 适合复杂状态管理，生态成熟 |
| 后端框架 | FastAPI | Python 异步框架，性能好，自带 API 文档 |
| 数据库 | SQLite | 实验室单机场景，零配置部署，WAL 模式够用 |
| 实时通信 | WebSocket | 2 秒推送，比轮询省带宽 |
| GPU 采集 | pynvml | NVIDIA 官方 Python 绑定，直接读驱动数据 |
| 系统采集 | psutil | 跨平台系统资源采集标准库 |
| 桌面版 | Electron | 一键启动所有服务，Windows 安装器 |
| 图表 | ECharts | 国产开源图表库，大数据量渲染性能好 |
| 样式 | TailwindCSS 4 | 原子化 CSS，开发效率高 |

### 部署方式（三种）

1. **Web 方式**：后端跑一个命令，前端构建后自动托管，浏览器访问 `localhost:8000`
2. **桌面安装器**：Windows 双击安装，自动拉起 Agent + Backend，打开独立窗口
3. **远程模式**：Backend 装在本地，Agent 装在远程 GPU 服务器上，通过"接入中心"连接

## 4. 算法亮点（说人话版）

### 4.1 功耗预测：三种算法自动比赛

**问题**：想预测未来 24 小时的功耗趋势，但不同时间段数据特征不同，一种模型搞不定。

**方案**：同时跑三种算法，每小时用 RMSE（预测误差）比一次，自动选最准的。

| 算法 | 擅长什么 | 参数 |
|------|---------|------|
| EWA 指数加权平均 | 近期趋势跟踪，抗噪声 | α=0.3（越近的数据权重越高） |
| 线性回归 | 单调上升或下降趋势 | 最少 3 个数据点 |
| 二次多项式 | 波峰波谷（如白天高夜晚低） | degree=2，有反发散保护 |

**效果**：不用人为选模型，系统自己选。基准测试验证了选出来的确实是误差最小的。

**答辩记忆点**：
> "三种算法每小时比赛一次，RMSE 最低的上场。多项式有防发散保护——预测值超过历史最大值 3 倍就自动弃用，避免数学模型爆炸。"

---

### 4.2 公平性评分：6 个维度打分

**问题**：怎么量化"这个人占了太多资源"？不能凭感觉。

**方案**：给每个用户从 6 个维度打分（满分 100，越低越不公平）：

| 维度 | 权重 | 为什么 |
|------|------|--------|
| 显存超用 | 1.5（最高） | 显存是最稀缺资源，一旦占了别人用不了 |
| 功率超用 | 1.1 | 功率影响电费和温度，但可以动态调 |
| 任务数超用 | 0.8 | 任务多不等于资源多，权重最低 |
| 长时间运行 | 最高扣 18 分 | 跑太久不让别人用，该扣分 |
| 可延迟任务惩罚 | 超额时翻倍 | "又占多了又不急"最不合理 |
| 紧急任务加分 | 最高加 15 分 | 合理的紧急需求应该被保护 |

**效果**：
- 1 个用户独占 → 100 分（没人跟你争，当然公平）
- 2 个用户均分 → ≥85 分
- 1 个人占了 80% 显存 → <60 分（红色警告）

**答辩记忆点**：
> "权重按资源稀缺性排列：显存最稀缺所以权重最高 1.5，功率次之 1.1，任务数最低 0.8。可延迟任务超额时惩罚翻倍——既占多了又不急，是最不合理的情况。"

---

### 4.3 让路排序：谁先让出资源

**问题**：功耗超预算了，要暂停一些进程，先暂停谁？

**方案**：5 个因素综合打分，分高的先让路：

| 因素 | 计算方式 | 效果 |
|------|---------|------|
| 优先级 | 可延迟=100 分，普通=55 分，紧急=0 分 | 不急的先让 |
| 超用程度 | 份额超用比例 × 2.2 | 占多了先让 |
| 显存占用 | 显存 GB × 4.0（上限 30） | 释放大内存价值高 |
| 运行时长 | 跑了几小时（上限 20） | 跑久了该轮换 |
| 违规次数 | 违规次数 × 28.0 | 屡犯的先让 |

**安全规则**：紧急任务**永远不会**出现在让路列表里，不管其他分数多高。

**答辩记忆点**：
> "让路排序有 5 个因素，分数高的先让。但有一个硬性规则：紧急任务永远不让。被测试验证过。"

---

### 4.4 三层混合调度

**问题**：怎么在不破坏用户训练的前提下自动管理功耗？

**方案**：三层调度，从硬到软：

| 层 | 名称 | 做什么 | 例子 |
|----|------|--------|------|
| 第 1 层 | 规则引擎 | 硬性安全规则，无条件执行 | 温度 ≥90°C → 立即限到 200W |
| 第 2 层 | 功率预算 | 总功率超了就自动压缩 | 预算 1200W，实际 1400W → 按优先级降频 |
| 第 3 层 | AI 调度 | LLM 分析全局生成优化建议 | "建议把 GPU 2 降到 220W 因为利用率只有 15%" |

**执行顺序**：每次 tick（2 秒），先跑规则引擎（保命），再跑预算引擎（保钱），最后跑 AI 引擎（优化）。

**答辩记忆点**：
> "三层调度各管各的：规则引擎管安全底线，功率预算管电费，AI 管优化。顺序不能乱——安全永远第一。"

### 4.5 碳排放追踪

**关键数字**（答辩人请记住这几个）：
- **碳因子**：0.5703 kgCO₂/kWh —— 来源是 2023 年中国国家电网公布的全国平均值
- **电价参考**：0.85 元/kWh（商业用电参考值）
- **等效树木**：1 棵树年吸碳约 21.77 kg（联合国环境规划署数据）

**举例**：4 张 GPU 平均 250W 跑一整天 = 24 kWh = 13.69 kg CO₂ = 需要 0.63 棵树吸收一年。

**答辩记忆点**：
> "碳因子 0.5703 来自国网 2023 官方数据，不是我们编的。系统会把每度电转成碳排放、换算成树木数量，让节能可感知。"

### 4.6 效率评分

**公式（简化版）**：效率 = GPU 利用率 ÷ 功耗比率

高利用率 + 低功耗 = 高效率。如果温度太高，还会打折：
- ≥85°C：打 8 折（GPU 已经过热降频了）
- ≥75°C：打 9 折（接近保护阈值）

所有对外输出（API 返回、WebSocket 推送、导出报告、AI 对话上下文）都会自动脱敏：

- 文件路径 → `[path]`

## 6. 预设 Q&A（20 题）

### 大数据相关（赛道核心）

**Q1：你们处理的数据规模有多大？**
> 6 张数据表，2 秒采集一次，7 天自动清理。首页有数据统计卡可以实时看到总记录数、采集时长和吞吐率。

**Q2：为什么用 SQLite 不用 InfluxDB 这种时序数据库？**
> 面向实验室单机场景，SQLite 零配置、零依赖，WAL 模式下读写并发够用。如果要扩展到集群，可以平滑迁移到 PostgreSQL。

**Q3：数据量大 10 倍你们撑得住吗？**
> 当前 SQLite 的瓶颈在单写者锁。对于单实验室场景（4-8 张 GPU）绰绰有余。如果升级到几十台服务器的集群，需要换成 PostgreSQL + 连接池，架构层面已经预留了接口抽象。

**Q4：采集频率为什么是 2 秒？**
> GPU 状态变化的有效时间尺度是秒级（温度突增、功耗突增）。2 秒兼顾实时性和数据库写入开销。低于 1 秒对 SQLite 压力太大，高于 5 秒可能错过温度突变。

### 算法相关

**Q5：EWA 的 α=0.3 怎么选的？**
> α=0.3 意味着最近 1 小时的数据权重是 3 小时前的 1.8 倍。太大（如 0.8）对噪声过敏，太小（如 0.05）跟不上趋势。0.3 是经验值，在我们的基准测试中表现稳定。

**Q6：三种预测算法各自适用什么场景？**
> EWA 适合短期（数据噪声大），线性适合单调趋势（如任务逐步增加期），二次多项式适合日周期波峰波谷。自动择优以 RMSE 为标准，每小时重新选。

**Q7：公平性评分的 6 个权重为什么这么设？**
> 按资源稀缺性排列：显存一旦占了别人用不了（1.5），功率可以动态调（1.1），任务数影响最间接（0.8）。基准测试验证了边界行为：单用户满分、均分高分、垄断低分。

**Q8：为什么不用机器学习模型做预测？**
> 实验室数据量不够训练 ML 模型。EWA/线性/多项式是可解释的统计方法，参数可论证、行为可预测。比黑盒模型更适合治理场景——你需要知道"为什么预测这个值"。

**Q9：碳因子 0.5703 的来源？**
> 2023 年中国国家电网公布的全国平均排放因子。如果要适配其他地区，这个值是可配置的。

### 工程相关

**Q10：前后端怎么通信？实时性怎么保证？**
> REST API 处理请求响应（50+ 个接口），WebSocket 处理实时推送（2 秒间隔）。WebSocket 断开后自动指数退避重连。

**Q11：演练模式和真实执行怎么隔离？**
> 所有危险操作都有 `dry_run` 参数。演练时不调 Agent、不改 GPU 状态，只返回"如果执行会怎样"。真实执行需要额外的 `acknowledge_risk` 确认。前端有风险确认复选框。

**Q12：为什么选 Vue 3 + FastAPI？**
> Vue 3 Composition API 适合管理复杂状态（8 个页面、30+ 标签页）。FastAPI 异步性能好，自带 Swagger 文档，和 pynvml/psutil 同为 Python 生态，前后端技术栈统一。

**Q13：隐私脱敏具体怎么做的？**
> 用户名用 Blake2S 哈希（稳定映射），文件路径正则替换为 `[path]`，命令行截断 160 字符。所有对外接口（REST、WebSocket、LLM 上下文、导出报告）统一过脱敏层。

### 实际价值

**Q14：这个系统在实验室真的跑过吗？**
> 系统在我们的 4×RTX 3090 实验室环境中开发和测试。没有真实 GPU 时有模拟模式（自动生成 4 张卡的逼真数据），保证全链路可演示。

**Q15：和 NVIDIA DCGM / Slurm 相比有什么优势？**
> DCGM 是监控工具，只看不管。Slurm 是作业调度系统，面向 HPC 集群。我们的定位是“智算中心优化代码生成系统”——轻量部署（单机即可）、治理导向（不只监控还能操作）、有演练模式和公平性量化。

**Q16：如果要推广到多台服务器怎么办？**
> 架构已支持远程 Agent 接入（前端"接入中心"可动态切换）。多后端的水平扩展需要换数据库和加消息队列，但 Agent 协议不变。

### 可能被挑战的弱点

**Q17：SQLite 并发写入瓶颈怎么办？**
> 面向实验室单机场景，WAL 模式 + 批写入已经够用。如果数据量翻 10 倍需要升级，迁移路径是 PostgreSQL + asyncpg，DataStore 接口层已经抽象好了。

**Q18：没有真正的深度学习模型算不算缺陷？**
> 治理场景需要可解释性。EWA/线性/多项式的参数每一个都有物理意义和测试验证。ML 模型在我们的数据规模下反而不如统计方法稳健。

**Q19：LLM 依赖外部接口，离线怎么办？**
> LLM 是增强功能，不是必需功能。所有核心治理（规则引擎、预算引擎、公平评分、告警检测）都不依赖 LLM。没有 LLM 时 AI 相关功能降级为"规则引擎 + 降级报告"，不影响主流程。

**Q20：前端代码量大，维护性怎么样？**
> 核心视图通过 composable 共享跨页面逻辑（如 `useExecutionMode`、`useActionFeedback`），业务组件按领域拆分到 `components/{domain}/` 目录下。TaskManager 从 1107 行拆到 600 行，关键模块都有独立组件。
