# SSH Linux 部分 GPU 可用性设计

## 背景

当前 SSH Linux provider 使用单条整机级 `nvidia-smi --query-gpu=...` 查询 GPU 状态。只要其中任意一张卡异常，整条命令就会非零退出，导致：

- `get_all_gpus()` 整体失败；
- 导入扫描直接判定目标不可用；
- 即使其他 GPU 正常，也无法导入和治理。

这与实际运维需求不符。目标行为应为：坏卡显式暴露，可用卡继续采集和治理。

## 目标

- 单张 GPU 异常时，不再让整机扫描失败。
- 扫描结果同时返回可用卡和异常卡。
- 异常卡明确标注状态和错误原因，不允许导入和治理。
- 只要至少存在一张可用 GPU，SSH 扫描就视为成功。
- 如果全部 GPU 都不可用，扫描继续显式失败，并返回汇总错误。

## 非目标

- 不处理 Windows 目标机。
- 不引入静默降级或 mock 数据。
- 不改动已有治理动作协议；异常卡仅通过“不可选、不可治理”被排除。

## 方案选择

采用“按卡采集”的方案，而不是继续依赖整机级查询后再兜底回退。

### 采集流程

1. 先通过稳定的轻量查询获取卡清单：
   - `index`
   - `uuid`
   - `name`
   - `pci.bus_id`
2. 对每张卡独立执行 `nvidia-smi -i <index> --query-gpu=...`。
3. 单卡查询成功：
   - 返回现有 GPU 指标；
   - 标记 `available: true`、`status: "ok"`。
4. 单卡查询失败：
   - 保留基础身份字段；
   - 指标字段置零；
   - 标记 `available: false`、`status: "error"`；
   - 记录 `error`，内容来自该卡查询命令的真实 stdout/stderr。

### 成功判定

- 至少 1 张 `available: true`：扫描成功。
- 0 张可用卡：扫描失败，错误信息汇总所有异常卡原因。

## 数据结构

在现有 GPU 字段基础上新增：

- `available: bool`
- `status: str`
- `error: str`
- `pci_bus_id: str`

约定：

- 可用卡：`available=true`，`status="ok"`，`error=""`
- 异常卡：`available=false`，`status="error"`，`error` 为真实原因

现有依赖数值字段的后端/前端逻辑继续可运行，因为异常卡的数值字段保持为 `0`，但业务逻辑必须额外依据 `available` 判断是否可治理。

## 后端改动

### `ssh_linux_provider.py`

- 抽出“枚举 GPU 基础身份”和“按卡采集指标”的逻辑。
- `get_all_gpus()` 返回完整 GPU 列表，含异常卡。
- `get_processes()` 不再依赖必须成功的整机 GPU 查询，只基于可用卡建立 `uuid -> index` 映射。
- 保留命令失败 warning 日志，继续打印 `code/command/stdout/stderr`。

### `runtime_provider_manager.py`

- `probe_target()` 对 SSH provider 的成功与否不再只看 `get_all_gpus()` 是否抛错。
- 若 provider 返回 GPU 列表且至少有一张可用卡，则 probe 视为 `connected`。
- 若全是异常卡，则维持 `offline`，并透出聚合错误信息。

### `system_import.py`

- 扫描接口继续返回 `gpus` 全量列表。
- `success=true` 时仅默认选中可用卡。
- 提交导入时只允许导入可用卡；若请求中含异常卡索引，返回明确 400。

## 前端改动

### 验机页

- 显示全部卡。
- 异常卡使用明确状态标签，如“不可用”。
- 卡片上展示错误摘要。

### 选卡页

- 异常卡保留在列表中，但禁选。
- “全选”只选可用卡。
- 已选摘要只统计可用且已选的卡。

## 错误模型

- 单卡失败时不隐藏错误，错误直接展示在该卡对象和日志中。
- 全卡失败时仍然显式失败，不伪造“扫描成功但空列表”。
- 导入请求若包含异常卡，明确拒绝并指出 GPU 索引。

## 测试策略

### 后端单测

- 一张卡正常、一张卡异常时：
  - `get_all_gpus()` 返回两张卡；
  - 异常卡带 `available=false` 和错误文本；
  - provider 扫描整体成功。
- 全部 GPU 异常时：
  - 扫描失败；
  - 错误信息包含所有异常卡摘要。
- `get_processes()` 在存在异常卡时仍能解析可用卡上的进程。
- 导入提交拒绝异常卡索引。

### 前端测试

- 扫描成功后默认仅选中可用卡。
- 选卡页异常卡不可点击。
- “全选”不会选中异常卡。

## 风险与取舍

- 按卡采集会增加 SSH 命令次数，但扫描频率低，复杂度换稳定性是值得的。
- 异常卡数值指标归零可能影响少量纯数值统计；因此所有治理入口必须基于 `available` 而不是仅凭数值判断。
