# Dashboard 巡检总表卡设计

## 背景

当前总览页的 `巡检` 区域由三段松散内容组成：

- 顶部 `主体巡检` hero 区，负责给出本轮巡检结论。
- 中间四张 facts 卡，展示导入范围、实时连接、AI 助手与 WebSocket 状态。
- 下方优先检查项列表与“查看全部健康项”按钮。

这套结构的问题不在信息缺失，而在表达方式：

- 异常项被渲染成连续长条，视觉上像日志列表，和总览页其它模块不协调。
- 结论、状态块和动作入口彼此分散，首屏没有明确主视觉。
- “查看全部健康项”像额外附着的一层，而不是巡检区域的自然组成部分。

用户已经明确，本轮只优化 `总览 -> 巡检` 这一块，不改其它 tab，不扩散到全站同类区域。

## 目标

- 把 `巡检` 区域重构成一张更完整的状态仪表板总表卡，去掉当前“长条检查清单”的观感。
- 让用户进入该页签后，第一眼就能判断：整体是否健康、当前最优先处理什么。
- 继续使用真实巡检数据，不引入 mock、静默 fallback 或新的后端接口依赖。
- 尽量复用现有 `buildDashboardHealthModel()` 的数据语义，避免为一次局部 UI 改造重写整条数据链。

## 非目标

- 不重构 `概览`、`实时态势` 或其它一级页面。
- 不改后端 `/system/self-check`、`health` 或导入范围的生成逻辑。
- 不把巡检页变成新的治理中心，不新增跨页工作流。
- 不删除健康项明细能力，只调整默认展示层级。

## 范围

本次设计聚焦以下前端区域：

- `frontend/src/components/dashboard/DashboardHealthTab.vue`

允许的轻量配套调整：

- `frontend/src/lib/dashboardPageModels.js`
- `frontend/src/lib/dashboardPageModels.test.js`
- 针对结构与样式层级的前端结构测试

本次不涉及新的接口字段，也不要求修改 dashboard 的整体路由和 tab 结构。

## 设计结论

采用 `B2 · 巡检总表` 方案：把当前散开的 hero、facts 卡、异常入口和展开按钮收进同一张总表卡中，形成“总表外壳 + 状态块 + 动作条 + 折叠明细”的单体结构。

选择这个方案的原因：

- 它最符合“状态仪表板”的方向，首屏更完整，不再像三段拼接内容。
- facts 卡仍然保留，但会成为总表内部的一层信息，而不是独立模块。
- 异常入口与展开明细的关系更明确，用户不会先看到一串长条，再理解它属于巡检区域。

## 信息结构

### 1. 顶部总表头

顶部区域负责承接当前 `summary.title` 和 `summary.message`，并追加一个右上角健康进度标签。

应包含：

- 左侧：`主体巡检` 标题、当前巡检主结论、简短说明。
- 右侧：健康进度标签，例如 `健康 3 / 4`。

健康进度标签不需要新的后端字段，可以从现有数据推导：

- 分子：`healthyChecks.length`
- 分母：`priorityChecks.length + healthyChecks.length`

当总检查数为 `0` 时，标签应退化为“等待巡检”，而不是展示 `0 / 0`。

### 2. 中部状态块

四张 facts 卡继续保留，但视觉上收进总表卡内部，形成一组紧凑状态块。

状态块继续沿用当前四个维度：

- 导入范围
- 实时连接
- AI 助手
- WebSocket

视觉规则：

- 默认使用统一紧凑卡片尺寸，不再出现大面积空白。
- 警告态只高亮对应状态块，例如 `AI 助手未启用` 可以使用 warning 样式。
- 非异常状态不做过度强调，保持总表整体整洁。

### 3. 底部动作条

总表底部使用一条紧凑动作条代替当前大块长条列表入口，承担“现在最值得处理的一项”。

动作条由三部分组成：

- 左侧 eyebrow：如“当前需处理项”或“当前无待处理项”
- 中部主文案：展示本次最优先的异常标签与其影响说明
- 右侧操作按钮：保留“查看全部健康项”入口

优先项选择规则：

- 如果存在 `priorityChecks`，以其中第一项作为当前主处理项；`priorityChecks` 的现有顺序视为模型已经给出的优先顺序。
- 如果存在多于一项的优先项，在主文案旁补一段次级提示，如“另有 2 项待关注”。
- 如果不存在优先项，动作条改为健康态文案，例如“当前无待处理项”，并保留展开健康项的能力。

这里不新增自动跳转动作，也不把按钮改成跨页 CTA。本区域仍然只负责展开本页巡检明细。

### 4. 折叠明细区

健康项和优先项的完整明细仍然保留，但不再默认占据首屏。

交互规则：

- 默认折叠明细区。
- 点击动作条右侧按钮后，展开完整检查清单。
- 展开后优先项仍然排在前面，健康项在后。
- 按钮文案在展开与收起之间切换。

展开区是补充信息，不是总表主体，因此视觉上应弱于顶部总表头和动作条。

## 数据映射

本次设计优先复用现有 `buildDashboardHealthModel()` 输出，避免无意义扩字段。

现有字段与新布局的对应关系如下：

- `summary.title` / `summary.message`
  - 用于顶部总表头主结论
- `factCards`
  - 用于中部四张状态块
- `priorityChecks`
  - 用于底部动作条主处理项，以及展开后的优先项列表
- `healthyChecks`
  - 用于健康进度统计，以及展开后的健康项列表

如实现阶段发现模板里为避免重复计算而需要增加轻量派生字段，允许在 `buildDashboardHealthModel()` 中补充纯派生数据，例如：

- `totalCheckCount`
- `healthyCheckCount`
- `primaryCheck`
- `remainingPriorityCount`

但这些字段必须完全由现有输入推导，不能引入新接口依赖。

## 状态规则

### 无异常

- 总表头展示健康进度。
- 状态块按正常态展示。
- 动作条展示“当前无待处理项”。
- 明细区默认折叠，可手动展开查看健康项。

### 存在 warning 或 critical

- 总表头继续展示整体结论，而不是把整个卡染成警报色。
- 底部动作条只突出一项主处理项。
- 对应状态块和动作条可使用 warning / critical 强调，但范围只限局部。

### 尚未拿到巡检结果

- 顶部继续使用当前默认文案：`等待巡检`。
- 健康进度标签显示“等待巡检”。
- 中部状态块仍可展示已知事实数据，例如导入范围和实时连接。
- 动作条显示暂无检查项，而不是伪造健康结论。
- 当总检查数为 `0` 时，不渲染右侧展开按钮，避免出现点开后仍为空白的伪交互。

## 视觉与布局规则

- 整个区域收敛为一张主卡，避免“上中下三段各自成块”。
- 卡内层次固定为：总表头、状态块、动作条、折叠明细。
- 首屏默认不出现长条式检查列表。
- 动作条应更像总表的一部分，而不是另一个独立面板。
- 警示色只用于局部状态，不把总览页变成高压告警页。

## 测试与回归要求

至少覆盖以下验证：

- `dashboard health model` 的派生语义仍正确，特别是优先项与健康项拆分。
- `DashboardHealthTab.vue` 的结构从“hero + 列表 + 按钮”转为“总表头 + 状态块 + 动作条 + 折叠明细”。
- 当没有 `priorityChecks` 时，动作条能稳定显示无待处理项文案。
- 当没有任何检查项时，不出现 `0 / 0` 或空白主结论。

本轮不需要新增后端测试，也不需要改接口契约测试。

## 实现边界

这次改造必须保持局部、可回归、可验证：

- 不动巡检数据拉取频率。
- 不改 dashboard 其它 tab 的数据模型。
- 不把异常项 silently 吞掉，展开区仍需完整暴露真实检查结果。
- 不为了视觉统一引入额外兜底状态或伪造动作入口。

最终交付应让 `巡检` 首屏更像“当前巡检总表”，而不是“被几根长条切开的检查清单”。
