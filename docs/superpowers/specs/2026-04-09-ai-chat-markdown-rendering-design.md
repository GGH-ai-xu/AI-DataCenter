# 2026-04-09 AI 问答消息 Markdown 渲染设计

## 背景

当前 AI 问答页已经接入真实流式输出，`frontend/src/views/AIAssistant.vue` 会持续接收 assistant 文本并实时更新聊天消息。

但消息展示层仍然把 assistant 回复按普通纯文本渲染：

- 标题如 `##`
- 强调如 `**加粗**`
- 列表、引用、表格、代码块

都会直接以原始 markdown 标记形式出现在界面上。

这会带来两个直接问题：

1. 长回复的结构被破坏，用户只能看到一大段带标记的原始文本，扫读成本很高。
2. 流式输出虽然已经打通，但由于最终展示层没有解析格式，实际可读性仍然偏差，无法体现 AI 问答的结构化价值。

用户已经明确本轮需求：

- 对 AI 问答回复进行格式解析
- 支持常用 markdown 之外，再额外支持代码块、引用和表格
- 不处理执行账本事件卡片，只处理 AI 问答区 assistant 消息

## 目标

- 让 AI 问答区 assistant 消息支持 markdown 渲染
- 支持本轮约定的 `B` 范围：
  - 标题
  - 加粗/强调
  - 段落与换行
  - 有序/无序列表
  - 引用块
  - 代码块
  - 表格
- 与现有流式输出链兼容，assistant 文本在增量更新时可以持续重新渲染
- 保持渲染链清晰、安全、可测试

## 非目标

- 本轮不改执行控制台 execution ledger 的事件展示
- 本轮不改用户消息展示，用户消息继续按纯文本显示
- 本轮不做自研 markdown 语法解析器
- 本轮不扩展到平台内其他富文本区域
- 本轮不引入伪流式、预渲染缓存或复杂的增量 AST 机制

## 用户确认的关键约束

### 1. 渲染范围

仅处理 AI 问答区中的 assistant 消息。

用户消息继续按纯文本展示，避免把普通输入误渲染成格式化文档。

### 2. 语法支持范围

采用 `B` 档：

- 标题
- 加粗/强调
- 列表
- 代码块
- 引用
- 表格

不追求“完整 markdown 规范全覆盖”，但要把当前这类长分析回复稳定渲染为可阅读内容。

### 3. 失败可见性

如果 markdown 解析或 HTML 清洗失败，不允许静默吞掉问题。

本轮采用显式可见的降级策略：

- 当前消息回退为纯文本展示
- 不伪装成“已经成功渲染”
- 不影响消息发送、流式接收和其他消息展示

## 方案对比

### 方案 A：成熟 markdown 解析器 + HTML 清洗

建议使用成熟 markdown 解析库，再通过 HTML 清洗库过滤渲染结果。

优点：

- 标题、列表、代码块、引用、表格支持稳定
- 对流式更新场景兼容较好
- 后续样式和渲染策略可以独立演进

缺点：

- 需要新增前端依赖

### 方案 B：手写受限 markdown 子集解析器

只解析当前需要的几类语法。

优点：

- 零依赖
- 完全可控

缺点：

- 表格、代码块、多段落边界容易出错
- 维护成本高
- 会把简单展示需求变成 parser 开发任务

### 方案 C：只做文本预处理

例如把 `##`、`**`、列表前缀做简单替换。

优点：

- 改动最小

缺点：

- 不足以支撑代码块、引用、表格
- 实际观感依旧接近“原始文本”

## 设计结论

本轮采用 `方案 A`。

原因如下：

- 用户已经明确需要 `B` 档支持，手写解析和文本替换都不稳
- 当前 AI 回复内容天然偏结构化，成熟解析器更适合直接接入
- 只要把解析和清洗封装在独立模块里，依赖引入不会污染现有页面逻辑

## 总体架构

### 1. 渲染职责拆分

本轮将聊天区渲染职责拆成三层：

- `frontend/src/views/AIAssistant.vue`
  - 继续负责流式接收、消息状态管理、发送逻辑
- `frontend/src/components/agent/AgentChatPane.vue`
  - 继续负责消息列表、输入区和建议按钮
- 新增 markdown 渲染层
  - 负责 assistant 消息的 markdown 转换、安全清洗和 HTML 输出

这样可以保证：

- 流式状态机不和展示实现耦合
- markdown 渲染能力可复用
- 失败边界只留在消息展示层，不污染整个问答链路

### 2. 推荐的文件边界

新增或调整的核心边界如下：

- `frontend/src/lib/agentMarkdown.js`
  - 统一封装 markdown 解析与清洗
- `frontend/src/components/agent/AgentChatMessageBody.vue`
  - 按消息角色决定是纯文本还是 markdown 渲染
- `frontend/src/components/agent/AgentChatPane.vue`
  - 改为使用 `AgentChatMessageBody`

这三个层级分别负责：

- 解析工具层
- 展示策略层
- 聊天列表容器层

## 渲染策略

### 1. 用户消息

用户消息维持纯文本渲染：

- 不解析 markdown
- 不渲染 HTML
- 保持输入即显示

这样更符合聊天输入的预期，也减少安全和语义误判。

### 2. Assistant 消息

assistant 消息走：

`markdown 文本 -> parser -> sanitize -> safe HTML -> 渲染`

渲染结果目标：

- 标题层级有明确字号和留白
- 列表具备层次缩进
- 代码块使用独立底板与等宽字体
- 引用块用侧边强调线区分
- 表格保持紧凑样式并允许横向滚动
- 长段落具备合适行高，不再糊成一整坨

### 3. 流式更新兼容

当前 AI 问答流式输出会不断更新 assistant 文本。

本轮不做“增量 AST”或“增量块级解析”，而采用更直接、稳定的方式：

- 每次 assistant 文本更新后，重新对当前完整文本做一次 markdown 渲染

选择这一策略的原因：

- 当前消息规模有限，性能成本可接受
- 实现稳定性远高于局部增量解析
- 更容易和现有 stream reducer 对接

## 安全设计

assistant 消息的 markdown 渲染最终会落到 HTML 输出，因此必须进行清洗。

本轮要求：

- 使用成熟的 HTML sanitize 方案
- 禁止未清洗的原始 HTML 直接进入 `v-html`
- 允许 markdown 生成的安全标签通过
- 禁止脚本、事件属性和危险 URL 注入

只有在经过清洗后，消息组件才允许以富文本形式挂载。

## 失败处理

### 1. 解析失败

如果 markdown 解析报错：

- 当前消息回退为纯文本展示
- 保留原始文本内容
- 不阻塞其他消息继续渲染

### 2. 清洗失败

如果 sanitize 阶段异常：

- 同样回退为纯文本展示
- 不做假成功

### 3. 作用域约束

失败只影响当前 assistant 消息本身，不影响：

- 流式接收
- 消息状态管理
- 输入框发送
- 其他消息展示

## 样式设计

本轮样式目标是“阅读型排版”，不是增加视觉噱头。

重点处理：

- assistant 消息中的标题层级
- 列表和段落的垂直节奏
- 代码块的独立视觉底板
- 引用块的弱强调边框
- 表格的紧凑边框与横向滚动容器

要求：

- 样式必须适配当前深色/亮色主题变量
- 不引入过重的装饰
- 不破坏现有聊天气泡结构

## 测试与验证

### 1. 单元测试

新增前端单测，覆盖：

- 标题与加粗渲染入口
- 列表渲染入口
- 代码块渲染入口
- 引用块渲染入口
- 表格渲染入口
- 解析失败时回退为纯文本

### 2. 结构测试

更新仓库结构测试，确保：

- `AgentChatPane.vue` 不再直接把 assistant 消息当纯文本输出
- 新增的 markdown 渲染组件已接入 AI 问答页

### 3. 构建验证

执行前端生产构建，确认：

- 新增依赖安装正确
- Vue 模板和模块导入无误

### 4. 手动验证重点

使用长格式的 AI 告警/分析回复验证：

- 标题是否正确分层
- 列表是否可扫读
- 表格是否可见且不炸布局
- 代码块和引用是否有清晰区分
- 流式生成过程中内容是否稳定更新

## 设计结论摘要

本轮将为 AI 问答区 assistant 消息增加独立、安全、可测试的 markdown 渲染层。

采用“成熟 parser + sanitize + 独立消息渲染组件”的方式，既满足当前 `B` 档格式需求，也能与已经落地的流式输出链直接兼容，同时把失败边界限制在单条消息渲染层，避免影响整条问答链路。
