# 2026-04-09 AI 助手统一聊天工作台设计

## 背景

当前 `frontend/src/views/AIAssistant.vue` 将 AI 能力拆成三个子页：

- `执行控制`
- `对话解释`
- `模型配置`

这套拆分在早期能快速落地，但已经暴露出明显的体验问题：

1. `执行控制` 与 `对话解释` 被强行拆开。用户需要在“提要求”“补充上下文”“看 Agent 执行过程”“做审批”“回看结果”之间来回切页，交互天然割裂。
2. `执行控制` 页内部重复信息过多。左侧 `AgentControlDock`、`AgentControlSessionCard` 与右侧 `AgentRunOverviewBar`、`AgentExecutionLedger` 都在重复展示状态、事件数、轮次、LLM 请求等事实。
3. 页面纵向高度偏大。多个大卡片叠加后，真正重要的主线程内容反而被状态摘要、按钮墙和会话统计挤压。
4. Agent 的自然语言交互与运行态可视化没有统一叙事。当前 UI 更像“控制台 + 账本”，而不是一个能边对话边规划边执行的 Agent 工作台。

用户目标已经明确：

- `执行控制` 与 `对话解释` 合并。
- 页面尽量像一个统一聊天框，而不是两个并列面板。
- 左侧最多保留一个紧凑的会话记录栏。
- 一屏内完成发起、追问、审批、回看执行过程。
- 删除冗余组件，避免页面继续长高。

## 目标

- 将 AI 页面重构为 `统一聊天工作台 + 模型配置` 两个子页。
- 用一个统一聊天线程承载问答、计划、审批、工具调用、执行结果和错误反馈。
- 删除独立的大块执行控制面板和执行账本面板，让执行过程作为对话的一部分出现。
- 保留 Agent 的可观测性，但默认紧凑，只有用户主动展开时才显示详细执行信息。
- 保持“真实事件驱动”，不引入 mock 卡片或伪造结果。

## 非目标

- 本轮不重构后端 goal runtime 的核心能力定义与权限模型。
- 本轮不重做 `模型配置` 页的信息架构，只保留为独立二级页。
- 本轮不引入跨用户共享会话、标签检索、复杂筛选等历史管理系统。
- 本轮不把所有问答都强行改写成 runtime session；UI 统一不等于后端通道必须立即合并。

## 方案比较

本轮讨论过三类方向：

### 方案 A：固定左侧会话记录栏 + 中间统一聊天流

特点：

- 左侧只保留紧凑会话记录。
- 中间主区只有一条统一聊天线程。
- 审批、计划、工具调用、结果都嵌在消息流里。

优点：

- 最贴近“一个聊天框解决”的目标。
- 最容易删除现有重复状态卡。
- 历史会话入口仍然清晰。

缺点：

- 需要把现有执行账本重构为消息流里的事件卡，而不是独立右栏。

### 方案 B：不固定左栏，历史会话改抽屉

特点：

- 主区更纯粹，像普通聊天产品。
- 历史会话通过抽屉或弹层打开。

优点：

- 主区最干净。

缺点：

- 会话切换和回看历史轨迹的路径变长。
- 不适合治理类工作台的持续回看场景。

### 方案 C：继续保留双栏，只减少卡片

特点：

- 继续沿用 `控制区 + 账本区` 结构。

优点：

- 实现成本低。

缺点：

- 根问题不解决，仍然是“两个系统拼在一个页面上”。
- 问答与执行割裂的问题依旧存在。

## 设计结论

采用 `方案 A`：

- 左侧保留固定但紧凑的会话记录栏。
- 中间主区为统一聊天工作台。
- `执行控制` 与 `对话解释` 合并为同一个工作台子页。
- `模型配置` 保留为单独子页。

同时确定以下细化决策：

- 左侧会话记录栏采用 `紧凑列表`，每条只显示标题、状态点、时间。
- 审批动作采用 `A1` 方案，直接嵌入聊天流，不再额外增加固定底部审批条。
- 工具调用卡 `默认折叠成单行`，避免线程高度继续膨胀。

## 顶层信息架构

`AIAssistant.vue` 的二级导航从当前三项收敛为两项：

- `工作台`
- `模型配置`

删除：

- 独立的 `对话解释` 子页
- 独立的 `执行控制` 子页

替换为：

- 一个统一的 `Agent Workbench`

### 工作台页面骨架

页面只保留两列：

#### 左列：会话记录栏

职责只有一个：切换和回看会话。

每条记录只显示：

- 会话标题
- 状态点
- 最近更新时间

明确不显示：

- 多行摘要
- 事件统计
- LLM 请求次数
- 长段说明

#### 中列：统一聊天工作台

由三个稳定区域组成：

1. 顶部薄状态条
2. 中间聊天线程
3. 底部固定输入区

不再存在：

- 独立 `AgentControlDock`
- 独立 `AgentControlSessionCard`
- 独立 `AgentExecutionLedger`
- 独立 `AgentRunOverviewBar`
- 独立 `PlannerLivePanel`

## 顶部薄状态条

顶部状态条只承担全局提示，不承担详细说明。

最多显示：

- 当前模式
- 当前会话状态
- 是否有待审批动作

例如：

- `规则解析`
- `执行中`
- `待审批 1`

明确不放：

- 大块统计卡
- 最近错误长文本
- 轮次 / 事件 / LLM 请求的大号数字面板

这些信息如果需要，应进入线程中的消息卡或展开详情中查看。

## 统一聊天线程

### 基本原则

- 所有关键交互都通过聊天线程表达。
- 默认只展示摘要，不默认展开细节。
- 线程中的卡片必须来自真实消息或真实 runtime 事件，不允许伪造“好看的流程卡”。

### 线程中的消息类型

#### 1. 用户消息

标准聊天气泡，不区分“问答输入”和“执行输入”。

#### 2. Agent 普通回复

用于：

- 回答问题
- 解释状态
- 要求补充信息
- 总结执行结果

#### 3. 计划卡

当 Agent 形成可执行计划时，在消息流中插入一张紧凑计划卡。

默认只显示：

- 一句话计划摘要
- 风险等级
- 动作数量
- `展开详情`

展开后显示：

- 结构化动作列表
- 约束说明
- 风险提示

#### 4. 审批卡

审批卡直接嵌入聊天线程，不额外生成底部固定审批条。

默认显示：

- 待审批动作数量
- 风险提示
- `批准`
- `拒绝`

可选显示：

- 动作摘要
- 补充说明入口

审批卡必须与触发它的上下文相邻，保证用户在看见“为什么要做”之后立刻做决定。

#### 5. 工具调用卡

工具调用不再以大面板或独立账本展示，而是作为线程中的紧凑事件卡出现。

默认折叠成单行，例如：

- `已读取运行时快照`
- `已请求 LLM 规划`
- `已执行 scheduler.run_once`
- `已完成 power_limit.set`

用户点击展开后，才显示：

- 输入参数
- 输出结果
- 原始响应
- 错误详情
- 耗时

#### 6. 结果卡

执行成功后显示一张结果卡。

默认只显示：

- 一句话结果摘要
- 影响对象数量
- `查看详情`

#### 7. 错误卡

执行失败或 LLM 失败时显示错误卡。

默认显示：

- 失败步骤
- 错误原因
- 是否已切换到规则解析 / 是否终止

展开后显示原始错误文本和事件细节。

## 输入区

输入区固定在聊天线程底部，始终可见。

包含：

- 多行输入框
- 少量建议 chips
- 发送按钮

建议 chips 的角色是“快速填充或快速发送”，不再承担大按钮墙的职责。

明确删除：

- 当前执行控制页里的大块 quick controls 区
- 独立权限说明大段文案

权限与风险说明收敛到：

- 输入区附近的一行简短提示
- 审批卡内部的明确风险说明

## 问答与执行的统一方式

本轮采用 `统一前端工作台，保留后端双通道` 的策略。

原因：

- 目标是先解决页面冗余和交互割裂。
- 若本轮同时重做问答 runtime、session continuation 和统一后端协议，范围会显著膨胀。

### 前端路由策略

工作台中的每次输入先进入统一线程，然后按意图路由：

- 纯解释 / 纯问答：走现有 `openAiChatStream`
- 需要规划、审批或执行的请求：走现有 `startAgentRuntimeSession`

### 意图路由原则

- 明确控制意图：直接进入 runtime session
- 明确问答意图：直接进入 chat stream
- 模糊输入：不做静默猜测，插入一条轻量确认卡，让用户明确选择“解释”还是“执行”

这样可以避免新的 silent fallback，也能保证统一工作台下的行为仍然可理解、可调试。

## 会话记录栏规则

左侧会话栏按紧凑列表设计：

- 一屏尽量显示更多会话
- 当前会话高亮
- 状态通过点色 + 短标签表达

每条仅保留：

- 标题
- 状态
- 时间

标题建议优先取：

1. 用户首条输入的压缩版
2. 计划摘要
3. 兜底为时间戳命名

明确不显示多行 preview，避免左栏重新变高、变吵。

### 视图层职责

`AIAssistant.vue` 应从“大量状态 + 三个子页 + 多块 runtime 控件”的状态中心，收敛为：

- 管理统一工作台状态
- 管理模型配置状态
- 负责 chat / runtime 双通道的事件汇总

具体 UI 渲染和消息类型映射下沉到独立组件与 transform 层。

## 线程数据模型

需要新增一个统一的前端线程项模型，例如：

```ts
type AgentThreadItem =
  | { kind: 'user_message', ... }
  | { kind: 'assistant_message', ... }
  | { kind: 'plan_card', ... }
  | { kind: 'approval_card', ... }
  | { kind: 'tool_event', ... }
  | { kind: 'result_card', ... }
  | { kind: 'error_card', ... }
  | { kind: 'system_notice', ... }
```

该模型由两类输入转换而来：

- chat stream 消息
- runtime 事件流

核心要求：

- 同一个线程中可交错出现普通聊天消息与 runtime 卡片
- runtime 事件必须可折叠、可展开
- 展开前后的数据都来自同一份真实事件 payload

## 展示压缩规则

为避免页面重新变高，统一采用以下压缩规则：

1. 默认一条消息卡只展示一个摘要。
2. 工具调用卡默认单行折叠。
3. 计划卡只显示动作数量和一句话摘要。
4. 结果卡只显示一句结论。
5. 错误卡默认只显示失败原因，不直接展开原始堆栈。
6. 会话栏不显示多行摘要。
7. 顶部状态条不出现大数字统计卡。

## 可观测性保留规则

页面虽然更紧凑，但不能损失调试能力。

必须保留：

- LLM 请求事件
- LLM 成功响应事件
- LLM 失败事件
- Rule fallback 事件
- 审批事件
- StepStarted / StepCompleted / SessionFailed / SessionCompleted

这些信息不再以右栏账本形式集中展示，而是通过线程中的事件卡保留。

## 测试与验证

### 前端结构测试

需要新增或更新测试，确认：

- `AIAssistant.vue` 不再保留 `control/chat/model` 三页结构
- 工作台只保留会话栏和统一线程主区
- 不再引用 `AgentControlDock`、`AgentExecutionLedger`、`AgentControlSessionCard`、`AgentRunOverviewBar`

### 线程 transform 测试

需要覆盖：

- chat 消息转换为线程消息
- runtime 事件转换为计划卡 / 审批卡 / 工具调用卡 / 结果卡 / 错误卡
- 工具调用卡默认折叠
- 审批卡嵌入线程，而非生成固定底部控制条

### 行为测试

需要验证：

- 解释型消息仍可通过 chat stream 完成
- 控制型消息仍可创建 runtime session
- 模糊输入不会静默猜测，而会要求用户确认路由
- 审批通过和拒绝都能在统一线程中回显结果

## 风险与约束

### 风险 1：统一线程后信息过密

缓解方式：

- 默认折叠工具调用卡
- 计划 / 结果 / 错误卡只显示摘要

### 风险 2：chat 与 runtime 双通道合并后状态边界混乱

缓解方式：

- 统一线程模型，但保持通道来源字段
- 每个线程项记录 `source: chat | runtime | system`

### 风险 3：左侧会话栏再次膨胀

缓解方式：

- 从设计上禁止多行摘要
- 固定紧凑高度和单行信息密度

## 实施结论

本轮不再继续优化当前“控制台 + 账本”双栏，而是直接把 AI 页面收敛成一个真正的统一聊天工作台：

- 左边找会话
- 中间看线程
- 在线程里规划、审批、执行、回看结果

这是本轮减少冗余、降低页面高度、统一 Agent 叙事的最短路径。
