# 页面主体优先布局设计

## 背景

当前一级页面已经完成了多轮信息架构收口，但布局上仍然存在一个共性问题：

- 页面首屏的主视觉区域，经常先被说明卡、摘要卡、统计卡占据
- 真正承载“工作”的主体区，例如主 tab、主图表、主账本、主控制台，往往被压到第二屏或更靠后的位置
- 很多大卡信息密度较低，只承载标题、简短说明、2 到 4 个数字或几个状态 badge，但占用了最重要的首屏空间

这不是单个页面的视觉问题，而是一个统一的布局层级问题：页面在“先介绍自己”而不是“先进入工作”。

## 目标

建立一套适用于一级页面的统一布局规范，让首屏最大面积始终服务于页面主体，而不是被低信息密度摘要层抢占。

本次设计覆盖以下一级页面：

- 总览
- 治理
- 能耗
- 观察
- 告警
- 智能

不覆盖以下页面：

- 登录
- 导入准备页
- GPU 详情页

## 总体方向

本次布局收法已经确认采用 `A：主体直出`。

这意味着：

- 凡是页面已经具备完整的页面级标题摘要，就不再保留额外的壳层大头部
- 页面首屏应在最短路径内进入 tab、图表、账本或控制台
- 所有低信息密度摘要卡都必须被压缩、下沉或侧置，不能继续占据主体上方主轴

## 统一布局规范

### 1. 首屏最大面积必须属于主任务区

页面进入后，用户第一眼看到的最大区域必须是：

- 主 tab 区
- 主图表区
- 主账本区
- 主控制区

而不能是：

- 页面介绍卡
- 重复的摘要带
- 低信息密度数字卡组

### 2. 一个页面只能有一层标题摘要

一级页面只允许保留一层页面级标题摘要。

不能出现以下叠加关系：

- 壳层头部 + 页面摘要卡
- 页面摘要卡 + 统计带
- 标题卡 + 标题卡 + tabs

如果页面已经有完整标题摘要，其他同职能层必须删除或弱化到局部元素中。

### 3. tabs 必须进入首屏上半区

对于以工作流、观察、分析、治理为主的页面，tabs 不能被多层摘要带压到后面。

首屏结构应尽量接近：

1. 页面标题摘要
2. tabs / 主切换
3. 当前 tab 的主体内容

### 4. 低信息密度摘要不能独占一整层

以下信息属于低信息密度信息：

- 状态 badge
- 导入范围说明
- 2 到 4 个统计数字
- 一句页面说明

这些信息可以存在，但只能以三种方式出现：

- 并入标题行右侧
- 变成 tabs 上方的一条细摘要带
- 下沉到对应 tab 内部作为局部摘要

不能再单独占一整排大卡。

### 5. 页面说明文案只保留最短必要表达

页面文案不再承担“教育用户理解这个页面是什么”的主要职责。

页面结构本身必须说明用途，说明文案只保留：

- 当前页面角色
- 当前状态判断
- 当前是否需要采取动作

### 6. 工作台页默认先工作、后解释

以下类型页面默认按“先工作、后解释”处理：

- 治理
- 观察
- 告警
- 智能

说明、统计、背景信息只能服务主体，不能压过主体。

### 7. 分流页允许保留摘要，但仍只能保留一层

总览页属于分流页，可以保留一层较强摘要。

但即便如此，也不能出现：

- 摘要卡
- 统计卡带
- tabs
- 主体

四段连续堆叠。

## 逐页修复意见

### 总览页

对应文件：

- `frontend/src/views/Dashboard.vue`

现状问题：

- 页面已经去掉壳层大头部，但 `dashboard-summary` 本身依然过厚
- `dashboard-summary` 下方又单独接了一层 `dashboard-summary__quick-grid`
- tabs 和真正的总览主体被继续向下挤压

修复意见：

- 保留 `dashboard-summary` 作为唯一页面级摘要层
- 将 `dashboard-summary` 压缩为：
  - 标题
  - 1 条核心判断
  - 右侧 2 到 3 个 badge
- 移除当前独立的一整排 `quick-grid`
- `summaryQuickStats` 改为：
  - 下沉到 `overview` tab 内部作为局部概览
  - 或压缩成 tabs 下方的一条细摘要带
- tabs 必须直接进入首屏

目标结果：

- 首屏直接看到“总览判断 + tab 切换 + 当前工作区内容”
- 不再先看两层摘要，再进入主体

### 治理页

对应文件：

- `frontend/src/views/GovernanceLayout.vue`

现状问题：

- 已隐藏壳层大头部，但治理页自身还有 `WorkspaceSummary + stats-grid`
- 治理三个子页本身已经很重，`quickStats` 再占一整层会直接挤压即时处置、策略控制和复盘主体

修复意见：

- 保留 `WorkspaceSummary` 作为唯一页面级摘要层
- 将 `WorkspaceSummary` 压缩为：
  - 标题
  - 执行模式 badge
  - 治理台 badge
- 删除顶部整排 `stats-grid workspace-summary-strip`
- `headerModel.quickStats` 改为：
  - tabs 右侧微摘要
  - 或下沉到对应子页内部

目标结果：

- 用户进入治理页后，首屏应立刻看到：
  - 标题
  - tabs
  - 当前治理子页主体

### 观察页

对应文件：

- `frontend/src/views/MonitorCenter.vue`

现状问题：

- `WorkspaceSummary(title="系统观察")` 后面紧接一整排 `monitor-summary-card`
- tabs 被顶到更下面
- 系统全貌、训练进度、用户统计、任务时间线这些真正主体被二次摘要层拖慢进入

修复意见：

- 保留 `系统观察` 作为唯一页面级标题摘要
- 删除顶部三张 `monitor-summary-card`
- 将以下信息压缩到标题行或 tabs 区局部状态中：
  - 当前 tab 名称
  - 活跃用户数
  - 刷新状态
- tabs 必须紧跟标题摘要出现
- 各 tab 的样本量、训练数、时间线数改为对应 tab 内部局部指标

目标结果：

- 观察页首屏直接进入“标题 -> tabs -> 当前观察工作区”
- 用户不需要先读一整排样本统计卡

### 告警页

对应文件：

- `frontend/src/views/AlertCenter.vue`

现状问题：

- `WorkspaceSummary` 之后还有一层 `AlertSummaryPanel`
- 实时流、今日告警簿、历史归档这些真正主体区进入得偏晚

修复意见：

- 保留 `告警中心` 作为唯一页面级标题摘要
- 删除 tabs 前单独一层 `AlertSummaryPanel`
- 严重数、未确认数、新增数改为：
  - 标题行右侧 badge
  - 或 `realtime` tab 内局部摘要
- `AlertSummaryPanel` 若继续保留，只能放入某个 tab 内部

目标结果：

- 告警页首屏优先暴露当前告警流与待确认对象
- 统计信息服务告警主体，而不是阻挡告警主体

### 能耗页

对应文件：

- `frontend/src/views/EnergyOptimization.vue`

现状问题：

- 页面没有双头部，但 `ink-header` 下方紧跟一整条 `source-strip`
- 这三张卡的信息密度偏低，却占据了 tabs 与 KPI 主体之前的核心位置
- 真正重要的内容其实是：
  - KPI hero
  - 分析图表
  - 优化工作区
  - AI 洞察

修复意见：

- 保留 `ink-header`
- 删除顶部 `source-strip`
- 将数据源状态、预算状态、时段状态并入标题右侧 pill 组
- 将说明类文案压缩到可展开帮助或局部提示，不再占一整层
- 让 tabs 直接紧跟标题
- `overview` tab 的 KPI hero 区成为首屏主体

目标结果：

- 首屏不再先看数据源说明，再进入工作区
- 页面进入后立刻进入能耗判断与分析主体

### 智能页

对应文件：

- `frontend/src/views/AIAssistant.vue`

现状问题：

- 结构已经比其他页面干净
- 但 `WorkspaceSummary` 仍然可以进一步压薄
- `control` tab 的输入区和控制计划虽然已经是主体，但还能更早成为视觉中心

修复意见：

- 保留 `WorkspaceSummary`
- 将摘要层继续压缩为：
  - 标题
  - 可审核 / 需风险确认 / LLM 状态
- 不新增任何统计带
- `control` tab 首屏要直接看到：
  - 输入区
  - 风险状态
  - 计划生成区
- `model` tab 中的说明卡和元信息卡继续压缩，避免配置说明抢过表单本体

目标结果：

- 智能页成为真正的“控制台先行”页面
- 页面一进来就是控制，而不是解释

## 页面类型规则

为了避免后续又回到“每页凭感觉堆摘要卡”，本次定义页面类型规则如下：

### 分流页

当前仅总览页属于分流页。

规则：

- 允许一层较强摘要
- 不允许摘要层和统计层连续堆叠
- tabs 仍需尽快进入首屏

### 工作台页

包括：

- 治理
- 观察
- 告警
- 智能

规则：

- 首屏优先暴露 tabs 和主工作区
- 标题摘要只能保留一层
- 统计信息必须下沉或压缩

### 分析页

当前能耗页属于分析页。

规则：

- 允许保留状态型标题行
- 不允许在标题与主体之间插入低密度大卡层
- 图表和 KPI 主体必须成为首屏核心

## 优先级

### 第一优先级

- 观察
- 治理
- 总览

原因：

- 这三页最明显存在“主体被头部和摘要带挤压”的问题

### 第二优先级

- 告警
- 能耗

原因：

- 主体仍然清楚，但首屏进入工作区的速度偏慢

### 第三优先级

- 智能

原因：

- 页面已经接近主体优先，只需继续压缩说明层

## 非目标

本次设计不包括以下内容：

- 重做各页面内部组件样式语言
- 新增新的二级导航体系
- 改后端接口
- 调整侧栏导航信息结构
- 扩展到登录、导入、GPU 详情页

本次只解决一个问题：首屏主体不突出，被冗余的、低信息密度的大卡片抢占主轴。
