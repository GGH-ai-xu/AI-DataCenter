# Dashboard 总览页分舱瘦身设计

## 背景

当前控制台总览页由 `概览`、`巡检`、`实时态势` 三个子页面组成，但它们之间的职责边界不清晰：

- `概览` 和 `实时态势` 都在重复表达治理结论、公平状态、连接状态和建议动作。
- `巡检` 除了链路检查，还承载了部分摘要信息，导致它不像独立的诊断页。
- 数据层不区分当前页签，固定并发拉取治理、健康和巡检数据，即使用户只停留在某一个页签，也会触发整套检测。

结果是页面显得拥挤、重复、噪声高，且总览页与专门的 `TaskManager.vue`、`Scheduler.vue` 出现职责重叠。

## 目标

- 让总览页三个子页面具备明确且互不重叠的职责。
- 去掉重复摘要、重复判断和重复治理建议，让页面更干净、更容易扫读。
- 让用户在 5 秒内判断当前是否有异常、该去哪一个专页处理。
- 将 dashboard 的数据刷新改为按页签加载，减少无效请求和无意义巡检。
- 在不改变现有核心路由语义的前提下，提升总览页的视觉秩序和信息层级。

## 非目标

- 不新增新的业务模块或新的一级导航。
- 不重写任务页、调度页和风险页的核心功能。
- 不引入静默 fallback、mock 数据或隐藏错误的降级策略。
- 不改变当前控制台整体视觉语言，只重构信息组织和页面层级。

## 范围

本轮设计聚焦以下文件与其对应的职责边界：

- `frontend/src/views/Dashboard.vue`
- `frontend/src/components/dashboard/DashboardLiveWorkspace.vue`
- `frontend/src/composables/useDashboardData.js`

同时参考但不直接重构的承接页：

- `frontend/src/views/TaskManager.vue`
- `frontend/src/views/Scheduler.vue`

## 现状问题

### 1. 页面职责重复

`Dashboard.vue` 顶部摘要区已经展示了一轮导入范围、治理状态、公平指数和连接状态。进入 `概览` 后，又用 hero 区重复表达 `boardTone`、`governanceTip`、公平判断与来源说明。切换到 `实时态势` 后，`DashboardLiveWorkspace.vue` 再次展示一遍治理状态、公平指数、治理建议和来源状态。

同一层信息在不同 tab 被重复讲述，用户切换页签时感受到的是“换皮重复”，而不是不同工作区。

### 2. Dashboard 与专页边界不清

公平治理的详细内容已经由 `TaskManager.vue` 承接，预算治理和调度动作由 `Scheduler.vue` 承接，但 dashboard 仍在尝试承担摘要、判断、建议甚至动作导向，造成：

- 总览页本身信息密度过高；
- 用户难以判断哪些内容只看摘要，哪些内容需要去专页处理；
- 不同页面之间的职责边界不稳定。

### 3. 数据刷新没有按需加载

`useDashboardData.js` 当前固定每 8 秒请求：

- `/scheduler/status`
- `/health`
- `/governance/fairness`
- `/system/self-check`

这意味着无论用户停留在 `概览`、`巡检` 还是 `实时态势`，都会不断触发治理、公平与巡检请求。页面职责已经重复，数据层又把这些重复进一步固化。

### 4. 视觉层级过于拥挤

当前 dashboard 同时存在：

- 顶部摘要条
- 概览 hero
- 多组 insight 卡片
- 实时态势 hero
- 侧栏治理建议和公平来源卡

这些区域都在争夺“主视觉”，导致页面看起来每一块都像重点，最终没有真正的重点。

## 方案选择

采用“保留三页签，但强收口职责”的方案，而不是压成双页签或改为单页长内容。

选择理由：

- 改动面最可控，不会破坏当前控制台导航结构。
- 最容易对已有心智模型做小步修正，而不是彻底重画工作区。
- 可以直接把冗余问题拆成“页面职责重定义”和“按页签加载”两个明确动作。

最终页签建议命名为：

- `首页`
- `实时`
- `巡检`

保留三个工作区，但每个工作区只承担一种用户意图。

## 信息架构

### 首页

首页只负责“摘要 + 分流”，不再承担完整分析和实时监控职责。

保留内容：

- 单一顶部摘要条
- 关键状态卡
- 主工作入口
- 异常优先提醒

移除内容：

- 二次 hero 区
- 大段治理说明
- 完整公平分析
- 来源状态重复解释
- 长列表治理建议

首页结构建议为：

1. 顶部摘要条
   - 导入范围
   - 连接状态
   - 预算风险
   - 严重告警
2. 四个主入口卡
   - 进入治理台
   - 进入任务台
   - 进入风险台
   - 进入复盘台
3. 三张异常优先卡
   - 预算是否超限
   - 是否存在严重告警
   - 是否存在公平风险

首页的目标不是解释系统全貌，而是帮助用户快速决定“要不要处理事情”和“去哪个页面处理”。

### 实时

实时页只负责“现在发生了什么”，不再承载治理结论、公平摘要或来源说明。

保留内容：

- 硬指标卡
- GPU 实时矩阵
- 趋势图
- 轻量数据源提示

移除内容：

- `boardTone`
- `governanceTip`
- 公平指数 chip
- 治理建议列表
- 公平与来源说明块

实时页结构建议为：

1. 顶部指标卡
   - 当前总功率
   - 平均温度
   - 活跃任务
   - 严重告警
2. GPU 实时矩阵
   - 直接进入单卡详情
3. 图表区
   - 功耗趋势
   - 利用率分布
4. 辅助信息条
   - 当前数据源
   - 最近刷新时间

实时页的目标是让用户快速扫硬件、负载和异常热区，而不是在这里阅读治理判断。

### 巡检

巡检页只负责“哪里坏了、影响什么、怎么处理”，不再重复首页摘要。

保留内容：

- 巡检总结果
- 异常优先清单
- 健康项折叠查看

移除内容：

- 导入范围摘要
- 连接状态重复卡
- 与首页相同的总览数据卡

巡检页结构建议为：

1. 顶部巡检结论
   - 当前异常数量
   - 影响范围
   - 最近检查时间
2. 异常清单
   - 检查项名称
   - 状态
   - 影响说明
   - 建议动作
3. 健康项折叠区
   - 默认折叠，仅在需要时展开

巡检页的目标是把用户从“看信息”切换到“定位问题”。

## 页面取舍规则

为了避免未来再次回到“每个 tab 都做一点”的状态，本轮重构明确以下取舍规则：

- dashboard 只做摘要，不做完整治理分析。
- 公平治理详细内容只保留在任务页。
- 预算治理详细内容只保留在调度页。
- dashboard 不展示长建议列表，只保留一句当前判断或一个异常入口。
- 同一个状态只允许在 dashboard 中出现一次主表达，其他地方只能作为跳转入口或上下文标签存在。

## 数据加载设计

### 总原则

数据刷新必须跟随页签职责，而不是把所有数据都塞进一个公共刷新域。

### 首页加载

首页只加载轻量摘要数据，足够支撑：

- 导入范围
- 连接状态
- 预算风险摘要
- 严重告警数量
- 公平风险一句话判断

首页不加载完整的公平治理列表、候选让路列表或完整巡检清单。

### 实时页加载

实时页只加载运行态数据：

- GPU 实况
- 任务数和活动用户数
- 趋势图数据
- 告警计数

实时页不加载完整巡检结果，也不加载完整治理建议。

### 巡检页加载

巡检页只加载：

- `self-check`
- 链路健康状态
- 必要的接入状态摘要

巡检页不拉取完整的公平治理数据。

### 刷新行为

- 页签切换时，触发对应域的首次加载。
- 停留在当前页签时，仅刷新该页签需要的数据。
- 不再以 dashboard 为单位固定并发拉取全部治理、健康和巡检接口。

## 组件与职责拆分

### `Dashboard.vue`

职责收口为：

- 页签切换
- 摘要层编排
- 三个工作区的容器和跳转

不再在该文件内承载过多的二级判断拼装逻辑。

### `DashboardLiveWorkspace.vue`

职责收口为：

- 实时指标卡
- GPU 实时矩阵
- 趋势图与轻量辅助信息

需要从该组件中移除与治理摘要重复的内容，避免它继续扮演第二个首页。

### `useDashboardData.js`

职责重构为：

- 拆分首页、实时、巡检三个独立数据域
- 按页签决定 loader 和 refresh
- 只向页面暴露各自工作区需要的数据

不再提供一个默认绑定所有 dashboard 需求的大型治理 bundle。

## 视觉设计原则

### 1. Dashboard 只保留一个主摘要区

主摘要区只出现在首页顶部。实时页和巡检页不再使用重复 hero 结构。

### 2. 数字卡与动作卡分离

- 数字卡只负责表达状态或数量。
- 动作卡只负责承接跳转或下一步操作。

不再在同一张卡片内同时堆叠大段文案、多个指标和动作按钮。

### 3. 正常状态降噪

默认状态以中性色呈现，只有 `warning` 和 `critical` 使用高强调色。这样可以让真正的异常更容易被看见，也能让页面整体更安静。

### 4. 减少 badge 堆叠

单张卡只允许一个主状态标签。多个标签会破坏阅读主次，并让页面显得拥挤。

### 5. 通过留白建立层级

统一卡片间距、分区留白和标题节奏，让页面从“堆内容”转向“分层展示”。视觉舒适感主要依赖信息密度控制，而不是额外装饰。

## 兼容性与实现边界

- 保持现有路由不变。
- 保持现有核心页面入口不变。
- 不依赖新增后端接口才能完成本轮重构；优先在前端侧按职责拆分现有数据使用方式。
- 如果现有接口粒度过粗，可以先在前端停止无关使用，再视实现阶段决定是否需要追加更细粒度接口。

## 验证标准

重构完成后需要满足以下标准：

1. 用户进入 dashboard 后，能够明确区分 `首页`、`实时`、`巡检` 各自的用途。
2. `首页` 不再出现完整治理分析和实时矩阵，`实时` 不再出现治理摘要 hero，`巡检` 不再重复首页摘要。
3. 切换不同页签时，请求只覆盖当前页签所需数据，不再统一刷新所有治理与巡检接口。
4. dashboard 与任务页、调度页之间的职责边界更清楚，用户更容易知道去哪里处理问题。
5. 页面首屏信息量下降，但关键异常更容易被识别，整体观感更干净、更舒适。

## 风险与取舍

- 首页信息被明显压缩后，少数用户会觉得“细节减少了”。这是有意取舍，详细分析应回归专页，而不是继续堆在 dashboard。
- 将数据按页签拆分后，需要同步清理组件之间的共享依赖，避免旧的公共计算字段继续把职责重新耦合回来。
- 若实现时只改视觉而不改数据加载，页面虽然会看起来简洁，但后台仍会继续无效检测，因此本轮必须把“视觉重构”和“按需刷新”一起落地。
