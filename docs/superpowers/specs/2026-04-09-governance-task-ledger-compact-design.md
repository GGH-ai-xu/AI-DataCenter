# 治理页任务账本紧凑行设计

## 背景

当前治理页的任务账本由 [TaskProcessLedger.vue](/mnt/e/Code/AI-DataCenter/frontend/src/components/tasks/TaskProcessLedger.vue) 渲染，每条记录默认展开三块内容：

- 身份信息：进程名、PID、GPU、分类、用户、显存、CPU
- 治理信息：优先级、治理说明、命令预览
- 动作区：暂停、恢复、终止按钮，以及动作提示或只读提示

这套布局的问题不是信息不够，而是默认展示层级过重：

- 单条记录同时铺开“对象信息 + 说明信息 + 动作信息”，导致高度明显偏大。
- 用户浏览账本时，绝大多数时间只是在扫“这是什么进程、是否可治理、要不要点动作”，并不需要默认阅读完整说明和命令。
- 多条记录连续出现时，页面纵向长度增长过快，任务账本显得臃肿。

用户已经明确希望：

- 默认每条记录尽量压缩到 `1-2 个高度`
- 减少默认展示的信息
- 保留动作按钮
- 通过 `查看详情` 再显示完整信息

## 目标

- 把任务账本默认行压缩成紧凑双行结构，显著减少单条记录占用空间。
- 默认保留用户真正需要快速决策的内容：对象身份、优先级、动作按钮、资源占用、治理摘要。
- 把完整说明、完整命令和只读原因收进可展开详情区。
- 不改后端接口，不新增数据源，不改变现有筛选、搜索、优先级和对象动作能力。

## 非目标

- 不修改治理页搜索、筛选和导出逻辑。
- 不改变暂停、恢复、终止、优先级设置的业务规则。
- 不把账本改成表格页或外部抽屉页。
- 不新增 mock、fallback 或静默降级行为。

## 范围

本次设计聚焦以下区域：

- `frontend/src/components/tasks/TaskProcessLedger.vue`

允许的轻量配套调整：

- 针对治理页账本结构的前端结构测试
- 如确有必要，少量补充 `frontend/src/lib/governanceTaskLedger.js` 的纯前端 helper

本次不涉及新的接口字段，也不要求修改 [GovernanceActionsView.vue](/mnt/e/Code/AI-DataCenter/frontend/src/views/GovernanceActionsView.vue) 的数据流。

## 设计结论

采用“紧凑双行 + 行内展开详情”的账本布局：

- 默认每条只展示两层信息
- 保留优先级与动作按钮
- 完整说明、命令和原因进入当前行下方的详情折叠区

这样账本默认是一份可快速扫读的治理清单，而不是一组默认展开的大卡片说明书。

## 默认行布局

### 第一行：身份与动作主行

第一行承载用户最需要快速判断和操作的内容。

默认显示：

- 进程名
- PID
- GPU 编号
- 分类 badge
- 优先级选择器
- 动作按钮

布局目标：

- `进程名` 作为主标题，占据视觉焦点
- `PID / GPU / 分类` 作为紧凑 meta，不再单独占据大块区域
- `优先级` 与动作按钮直接放在主行右侧，避免用户上下寻找

这行的职责只有两个：

- 识别对象是谁
- 决定是否立刻操作

### 第二行：轻量摘要行

第二行只保留轻量辅助信息，不再默认展示完整说明块。

默认显示：

- 用户
- 显存
- CPU
- 一句治理摘要
- `查看详情` 按钮

治理摘要固定优先显示 `getReasonSummary(proc)`，而不是命令预览。

原因：

- 治理摘要直接服务于决策
- 命令是排错信息，不是默认浏览信息

这行应明显弱于第一行，但仍然足够让用户快速判断该进程是否值得展开。

## 展开详情

点击 `查看详情` 后，只在当前记录下方展开一个内嵌详情区，不跳页、不弹窗、不占右侧工作区。

展开后显示完整信息：

- 完整治理说明：`getManageableReason(proc)`
- 完整命令：`getCommandPreview(proc)` 或 `proc.command`
- 动作提示：`getActionHint(proc)`
- 不可治理时的只读原因

详情区设计要求：

- 默认收起
- 点击同一按钮可展开 / 收起
- 一次只展开当前点开的那一条，避免多个大详情区同时撑开账本
- 视觉弱于默认行，例如使用更轻背景、更细分隔和更小字号

详情区的目标是“补充信息”，不是把原来那一整套厚布局原样搬进折叠区。

## 可治理与只读状态

### 可治理进程

默认行中保留：

- 优先级选择器
- 暂停按钮
- 恢复按钮
- 终止按钮

展开详情中补充：

- 完整治理说明
- 完整命令
- 当前动作提示

### 不可治理进程

默认行中不保留对象动作按钮，改为紧凑只读状态表达，例如：

- `仅观测`
- `只读`

同时保留：

- 查看详情
- 资源信息
- 治理摘要

展开后明确展示：

- 为什么该进程不可治理
- 为什么只做观测

这样只读进程默认不会再占据一个完整动作面板，但仍然保留可解释性。

## 数据映射

本次设计优先复用现有 helper，不要求新后端字段。

默认行使用的现有数据与 helper：

- 进程名：`proc.name`
- PID：`proc.pid`
- GPU：`proc.gpu_index`
- 分类：`getCategoryLabel(proc)` / `getCategoryClass(proc)`
- 优先级：`proc.priority`
- 用户：`proc.username`
- 显存：`displayGpuMemory(proc)`
- CPU：`displayCpuPercent(proc)`
- 摘要：`getReasonSummary(proc)`

详情区使用：

- 完整治理说明：`getManageableReason(proc)`
- 命令：`getCommandPreview(proc)` 或 `proc.command`
- 动作提示：`getActionHint(proc)`

如果实现阶段为减少模板噪声需要增加轻量前端派生 helper，可以补充纯派生字段，但必须满足：

- 完全由现有数据推导
- 不新增接口依赖
- 不改变现有动作逻辑

## 交互规则

- `查看详情` 默认存在于每条记录上
- 展开后按钮文案切换为 `收起详情`
- 搜索、筛选或列表刷新后，如果展开项已经不在当前列表中，应自动关闭该展开态
- 优先级修改和对象动作仍在默认行完成，不要求先展开详情

## 布局与视觉规则

- 单条默认高度优先控制在“主行 + 摘要行”两层
- 去掉当前三栏大卡的厚重感，改成更像“紧凑账本条目”
- 默认行避免大面积说明文本
- 动作按钮保留，但应压缩到与主行对齐的紧凑区域
- 详情区应和默认行形成明显层级差，避免再次造成视觉拥挤

## 测试与回归要求

至少覆盖以下验证：

- `TaskProcessLedger.vue` 默认结构不再同时展示完整治理说明块和命令块
- 组件存在 `查看详情 / 收起详情` 的展开入口
- 默认行继续保留优先级选择和动作按钮
- 不可治理进程默认不渲染对象动作按钮，而改为只读状态提示

本轮不需要新增后端测试，也不需要修改治理页接口测试。

## 实现边界

- 不修改治理页的主布局、搜索栏和导出区
- 不重构治理页其它子页面
- 不为了压缩高度而删掉必要的操作能力
- 不隐藏真实错误或真实只读原因

最终交付应让任务账本默认更像“可快速扫读的治理清单”，而不是“每条都完全展开的治理说明卡”。
