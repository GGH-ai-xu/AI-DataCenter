# TaskManager 任务页双主轴重构设计

## 背景

当前任务页由 `待处置任务`、`公平治理`、`规则配置` 三个子页面组成，但三者之间存在明显的职责交叉：

- `待处置任务` 和 `公平治理` 都在展示“建议让路任务”；
- `公平治理` 和 `规则配置` 都在重复展示按用户聚合的状态；
- 页面顶部的摘要区明显偏向动作语义，却对所有页签常驻；
- 数据层无论停留在哪个页签，都会同时拉取任务和公平治理数据。

结果是：

- 页签切换后，用户看到的是“同一批信息换位置重排”；
- `公平治理` 页过于膨胀，既像诊断页，又像动作页，又像半个策略页；
- 页面轮询和首屏内容都比实际需要更重；
- 整个任务页看起来拥挤，重点不稳定。

## 目标

- 让任务页三个子页面具备稳定、互不重叠的职责边界。
- 保留“任务处置”和“公平诊断”两条主轴，但不再让两者重复承载同一信息。
- 让页面更干净、扫读更快，用户进入任一页签后能立即判断当前工作模式。
- 将数据刷新改为按页签加载，减少无效请求和无意义检测。
- 在不改变现有核心治理能力的前提下，优化组件边界和页面结构。

## 非目标

- 不新增新的一级导航或新的治理模块。
- 不改变任务动作协议，不引入新的治理动作类型。
- 不引入静默 fallback、mock 数据或隐藏错误的降级路径。
- 不整体重写控制台视觉体系，只重构任务页的信息组织和层级。

## 范围

本轮设计聚焦以下文件及其对应的职责边界：

- `frontend/src/views/TaskManager.vue`
- `frontend/src/composables/useTaskManagerData.js`
- `frontend/src/components/tasks/TaskProcessLedger.vue`
- `frontend/src/components/tasks/FairnessGaugeCard.vue`
- `frontend/src/components/tasks/UserRulesGrid.vue`

必要时允许新增任务页专属子组件，但不扩大到其他业务工作区。

## 现状问题

### 1. `公平治理` 页承担了过多职责

`公平治理` 当前同时展示：

- 公平指数；
- 用户占比结构；
- 治理建议；
- 建议让路任务。

其中前两项属于“诊断”，后两项分别属于“解释”和“动作候选”。这让该页从分析台膨胀成了半个操作台。

### 2. 动作候选被重复表达

“建议让路任务”同时存在于：

- `公平治理` 页右侧；
- `待处置任务` 页侧栏。

这会导致一个问题：用户不知道候选任务列表的主归属页到底是谁，也不知道在公平页看到候选任务后，是否可以直接在该页完成动作闭环。

### 3. 用户状态被重复表达

`公平治理` 页的用户分布条展示了每个用户的：

- 显存占比；
- 任务数；
- GPU 数。

`规则配置` 页的用户卡顶部又展示了：

- 当前任务数；
- GPU 数；
- 占比；
- 违规数。

这让 `规则配置` 页不再只是配置页，而开始重复承载诊断信息。

### 4. 常驻摘要区不符合页签语义

顶部摘要区显示：

- 可治理任务数；
- 紧急任务数；
- 治理显存占用。

这组摘要明显偏向 `待处置任务` 的动作语义，但当前在三个页签中统一常驻。用户切到 `公平治理` 或 `规则配置` 时，首先看到的仍然是动作统计，而不是该页签真正的核心上下文。

### 5. 数据加载没有按页签拆分

当前 `useTaskManagerData.js` 会统一并发请求：

- `getTasks()`
- `getFairnessGovernance()`

无论用户停留在哪个页签，都在持续刷新整套任务治理数据。这会带来：

- 多余请求；
- 轮询噪声；
- 页签职责被数据层进一步耦合。

## 方案选择

采用“保留三页签，但重定义为双主轴加一策略页”的方案。

### 方案对比

#### 方案 A：操作优先

让 `待处置任务` 成为绝对主工作台，其余两个页签退为附属页。

优点：

- 最容易落地；
- 最贴近当前操作链路。

缺点：

- 公平治理会被压成附属报告页；
- 不符合本次确定的“双主轴并重”方向。

#### 方案 B：双主轴并重

将任务页重构为：

- `任务处置`
- `公平诊断`
- `规则配置`

其中前两者都是完整工作台，但职责完全不同。

优点：

- 职责边界最清晰；
- 能保留动作治理与公平治理两条主线；
- 最有利于后续做按页签数据加载。

缺点：

- 需要明确迁移重复内容，不能只做排版微调。

#### 方案 C：单页合流

将任务处置和公平治理合为一个大页，规则配置单独保留。

优点：

- 用户少一次切换。

缺点：

- 页面会重新变胖；
- 容易回到“分析、建议、动作混在一起”的状态。

### 结论

采用方案 B。

本轮正式将三个页签的产品语义定义为：

- `任务处置`：筛选、分级、执行
- `公平诊断`：判断当前是否公平、为什么不公平、应朝哪个方向调整
- `规则配置`：定义用户规则和治理边界

## 信息架构

### 总体规则

- 三个页签保留统一的外层工作区骨架，但每个页签只允许存在一种主意图。
- 顶部不再使用同一组常驻统计卡，而是切换为“页签专属摘要”。
- 同一类信息只允许有一个主表达位置，其他位置只能保留轻量入口或跳转。

### 页签 1：任务处置

任务处置页是唯一允许展示具体治理动作和让路候选列表的页面。

保留内容：

- 搜索和优先级筛选；
- “仅治理任务 / 全部 GPU 相关进程”切换；
- 任务账本；
- 执行模式；
- 候选让路任务；
- 导出治理报告。

移除内容：

- 与公平诊断重复的用户占比解释；
- 与规则配置重复的用户规则说明。

页头摘要建议为：

- 可治理任务数；
- 紧急任务数；
- 当前执行模式。

布局建议：

- 主区：工具栏 + 任务账本；
- 侧栏：执行模式 + 候选让路任务。

### 页签 2：公平诊断

公平诊断页只做诊断和解释，不直接承担动作闭环。

保留内容：

- 公平指数；
- 用户资源占比；
- 当前倾斜等级；
- 治理建议；
- 偏斜原因摘要。

移除内容：

- 候选让路任务长列表；
- 可直接执行的暂停 / 恢复 / 终止按钮；
- 重复的执行模式说明。

页头摘要建议为：

- 公平指数；
- 偏斜用户数；
- 建议强度。

布局建议：

- 左区：公平指数与用户结构；
- 右区：治理建议与倾斜说明。

交互建议：

- 保留一个明确入口“查看建议让路任务”；
- 点击后切换到 `任务处置`，并带上预设筛选或聚焦状态；
- 不在本页复制一份候选任务卡片。

### 页签 3：规则配置

规则配置页只承担策略定义职责，不再承载完整诊断视图。

保留内容：

- 用户角色；
- 最大任务数；
- 最大 GPU 数；
- 显存额度；
- 是否允许让路；
- 备注。

仅保留最轻上下文：

- 当前负载；
- 是否违规。

移除内容：

- 用户占比条；
- 重复的公平解释；
- 长段治理建议。

页头摘要建议为：

- 活跃用户数；
- 违规用户数；
- 自定义规则覆盖率。

布局建议：

- 默认呈现紧凑规则卡或表格式卡片；
- 把编辑字段放在展开区或结构化表单中；
- 首屏优先让用户看清“谁需要配规则”，其次才是“具体怎么改”。

## 信息迁移规则

为避免未来再次出现重复，本轮重构明确以下归属：

- 候选让路任务列表：只属于 `任务处置`
- 公平指数与用户占比：只属于 `公平诊断`
- 用户规则编辑：只属于 `规则配置`
- 任务执行模式：只属于 `任务处置`
- 用户违规状态：主归属 `规则配置`，公平页只允许聚合判断，不重复逐用户状态卡

跨页只允许传递“意图”，不允许复制完整信息块。

示例：

- `公平诊断` 可以给出“建议优先释放高占比用户任务”，但不直接复制 5 条候选任务卡；
- `规则配置` 可以给出“当前该用户已违规”，但不重复展示完整公平占比条和诊断摘要。

## 组件边界调整

### `TaskManager.vue`

只负责：

- 工作区外壳；
- 当前页签状态；
- 页签级摘要切换；
- 跨页签跳转和轻量共享状态。

不再承载过多页内渲染细节。

### `TaskProcessLedger.vue`

继续作为任务处置主组件，专注：

- 进程身份；
- 治理说明；
- 动作入口。

不引入公平诊断内容。

### `FairnessGaugeCard.vue`

收口为纯诊断组件，专注：

- 公平指数；
- 倾斜等级；
- 用户结构可视化。

不再负责候选动作展示。

### `UserRulesGrid.vue`

收口为规则编辑组件，保留最小上下文信息。

建议将当前顶部冗余信息压缩为：

- 用户名；
- 当前负载摘要；
- 违规状态。

不再承担完整公平说明。

## 数据加载设计

### 总原则

数据刷新必须跟随页签职责，而不是按整个任务页统一刷新。

### 任务处置加载

进入 `任务处置` 时加载：

- `getTasks()`
- 任务账本所需摘要

仅当需要侧栏候选让路任务时，使用对应治理结果字段，不额外复制到其他页签。

### 公平诊断加载

进入 `公平诊断` 时加载：

- `getFairnessGovernance()`

该页签只刷新公平相关数据，不触发任务账本刷新。

### 规则配置加载

进入 `规则配置` 时加载：

- 用户规则；
- 必要的用户概要；

保存规则后，仅局部刷新规则与用户概要，不强制刷新整个任务账本。

### 共享状态

可跨页签共享的仅包括：

- 当前活动页签；
- 用户选择的跳转意图；
- 必要的轻量计数。

不共享整块重复 UI 数据。

### 轮询行为

- 页签首次进入时触发该页签的首次加载；
- 停留在当前页签时，仅刷新该页签需要的数据；
- 不再在任意页签下固定并发拉取 `tasks + fairness` 全量数据。

## 视觉层级设计

### 统一骨架

三页签继续使用统一的工作区布局语言，但不再共享同一套“统计卡 + 内容区”模板。

### 任务处置

- 强化账本作为主视觉；
- 侧栏只放与动作闭环直接相关的信息；
- 减少解释性文案，提升操作密度。

### 公平诊断

- 强化图形化表达和结构判断；
- 用一主一辅两列区分“看结构”和“看建议”；
- 不出现会误导用户立即执行动作的控件。

### 规则配置

- 视觉目标是稳定、安静、可扫读；
- 首屏避免一排输入框同时出现；
- 通过折叠、分段或更紧凑的表单结构降低压迫感。

## 命名建议

为让三页签意图更稳定，建议文案从当前：

- `待处置任务`
- `公平治理`
- `规则配置`

调整为：

- `任务处置`
- `公平诊断`
- `规则配置`

这样可以明确：

- 第二页是诊断页，而不是动作页；
- 第一页才是执行闭环入口。

若出于兼容原因暂不调整内部 key，可只修改展示文案，不强制修改路由或内部状态值。

## 验收标准

- 用户切换三个页签时，不再看到同一批信息重复出现。
- “建议让路任务”只在 `任务处置` 中出现一次主表达。
- `公平诊断` 中不再出现任务动作按钮或完整候选任务列表。
- `规则配置` 中不再出现完整公平占比条和重复诊断说明。
- 顶部摘要跟随页签切换，不再是统一常驻动作摘要。
- 数据刷新按页签拆分，停留某页签时不会继续无意义刷新其他页签数据。
- 页面第一屏视觉重点明确，用户能在 5 秒内理解当前页签的职责。

## 风险与取舍

- 按页签拆分数据后，跨页切换时首屏信息可能比当前多一次“首次加载”；这是用更低冗余换更稳定职责，值得接受。
- `公平诊断` 移除候选任务列表后，用户会多一次跳转，但换来的是“诊断”与“执行”边界清晰，减少误判和重复维护。
- `规则配置` 首屏信息压缩后，部分高级信息需要展开才能看到，但整体页面会更稳、更安静，也更符合策略页的使用方式。
