# 2026-04-10 AI 助手交互卡分组设计

## 背景

当前 AI 助手页面虽然已经收敛为统一聊天工作台，但线程内部仍然沿用“消息 / 事件平铺”的展示模型：

- 用户消息是一条卡片
- Agent 普通回复是一条卡片
- 计划是一张卡片
- 审批是一张卡片
- 工具调用是一张卡片
- 结果 / 错误又是各自独立的卡片

这会带来两个直接问题：

1. 用户很难区分“这些步骤属于哪一次交互”。一次输入之后会立刻长出多张散卡，但它们之间没有明确归属边界。
2. 即使系统内部确实有执行进展，视觉上也像“线程里不断追加碎片”，而不是“这次请求正在展开执行”。

用户的目标已经明确：

- 一次用户输入应当对应一张交互卡。
- 该次输入后产生的解释、追问、计划、审批、工具步骤、结果、错误，都收在这张卡里。
- 线程应该按“交互”区分，而不是按“事件类型”平铺。

## 目标

- 将 AI 助手线程的一级对象从 `item` 改为 `interaction`。
- 每条用户输入都生成一张交互卡，作为该次请求的唯一视觉容器。
- 将解释、追问、计划、审批、工具调用、结果、错误统一归属到对应交互卡内部。
- 让用户一眼能看出每次交互的边界、状态和进展。
- 保留已有 runtime 执行细节，但默认紧凑，按需展开。

## 非目标

- 本轮不修改后端数据库结构。
- 本轮不为 runtime event 增加新的持久化 `interaction_id`。
- 本轮不改 SSE 协议和后端 event schema。
- 本轮不重做运行时能力、审批模型或执行逻辑。
- 本轮不新增复杂的交互历史筛选、标签或检索系统。

## 现状问题

### 平铺模型不表达“交互”

当前线程 view model 的一级单位是消息和 runtime 事件，而不是交互本身。这意味着系统只能表达“发生了哪些片段”，无法表达“这些片段属于哪次请求”。

### 视觉层级错误

用户真正关心的是：

- 我刚才说了什么
- 系统现在理解成什么
- 进展到哪一步
- 最终结果是什么

而不是“一串没有归属关系的 plan / tool / result 卡片”。当前 UI 把技术事件暴露成了一级视觉对象，导致主线叙事被打碎。

### 继续堆样式不能解决根因

即使继续给平铺卡片加缩进、边框或分隔线，也仍然是“很多卡片”。这只能改善视觉噪声，不能建立明确的交互边界。

## 方案比较

### 方案 A：继续平铺，只增加分组样式

做法：

- 保留现有 `item[]`
- 通过背景色、缩进、竖线提示分组

优点：

- 改动最小

缺点：

- 一级对象仍然是碎片事件
- 交互边界依旧模糊
- 无法真正做到“一次交互一张卡”

### 方案 B：前端引入显式 `interaction[]` 视图模型

做法：

- 前端根据用户消息边界，将 `chatMessages + runtimeEvents` 重组为 `interaction[]`
- UI 渲染交互卡，而不是渲染平铺 item

优点：

- 能立即满足“一次交互一张卡”的目标
- 改动集中在前端工作台模型与组件层
- 不必同步修改后端存储

缺点：

- 交互归属规则仍由前端推导，而不是后端显式建模

### 方案 C：后端也显式引入 `interaction_id`

做法：

- 提交时生成 `interaction_id`
- 后续聊天回复和 runtime 事件都带该 id
- 前后端统一按交互建模

优点：

- 语义最完整
- 长期最稳

缺点：

- 会扩大到 runtime 数据模型和流协议改造
- 超出本轮优化范围

## 设计结论

采用 `方案 B`。

本轮先在前端引入显式 `interaction[]` 视图模型，把“一次交互”提升为线程一级对象。等 UI 和交互稳定后，如果确有必要，再把 `interaction_id` 下沉到后端真实模型。

## 核心概念

### Interaction

每次用户提交创建一个 `interaction`，它是线程中的一级对象。建议字段至少包括：

- `id`
- `userMessage`
- `status`
- `assistantReply`
- `runtimeCards`
- `stepSummary`
- `startedAt`
- `updatedAt`
- `expanded`

### Runtime Cards

`runtimeCards` 是交互卡内部的详细步骤集合，而不是线程一级对象。它继续承载现有能力：

- 计划卡
- 审批卡
- 工具调用卡
- 结果卡
- 错误卡

## 交互边界规则

本轮采用明确且简单的前端分组规则：

1. 每次用户提交都创建一个新的 `interaction`。
2. 该交互持有自己的用户输入。
3. 该交互之后出现的 assistant 回复归属到当前交互。
4. 该交互之后出现的 runtime 事件归属到当前交互。
5. 当下一条用户消息出现时，前一个交互封口。
6. 当前会话里任何尚未封口的执行进展，都归属到最近一个交互。

这个规则的目标不是完美表达所有未来并发场景，而是优先解决当前“无法区分每次交互”的核心问题。

## 交互卡结构

每张交互卡采用“上摘要，下步骤”的两层结构，默认紧凑。

### 1. 用户输入头部

展示：

- 本次用户输入文本
- 当前状态标签

状态标签建议只保留少量稳定状态：

- `处理中`
- `待审批`
- `已完成`
- `失败`

### 2. 助手回复区

用途：

- 展示解释类回答
- 展示追问类回答
- 执行类请求在尚未形成完整结果前，也可展示一句短摘要，例如“已进入执行链，正在生成计划”

原则：

- 助手回复是交互卡的重要摘要区，不再散落成线程里的独立卡片

### 3. 步骤摘要条

用途：

- 以紧凑的一行表达当前交互进展

例如：

- `计划`
- `审批`
- `执行`
- `完成`

规则：

- 当前步骤高亮
- 失败步骤标红
- 未发生的步骤不渲染

### 4. 详细步骤区

默认折叠，用户展开后才显示：

- plan card 详情
- approval card 详情与审批按钮
- tool event 详情
- result detail
- error detail

这样既保留执行透明度，又避免默认状态下线程过高。

## 状态模型

交互卡的状态建议由当前数据推导，不单独引入额外状态机持久化。

推荐规则：

- 仅有用户输入，尚无回复：`处理中`
- 有 assistant 追问或回答，未进入执行：`处理中`
- runtime 出现审批事件：`待审批`
- runtime 出现完成结果：`已完成`
- runtime 出现失败结果或错误事件：`失败`

## 组件结构调整

### 保留

- 现有 plan / approval / tool / result / error 子卡组件可以继续复用

### 新增

新增以下组件：

- `AgentInteractionList.vue`
  - 渲染交互卡列表
- `AgentInteractionCard.vue`
  - 单张交互卡容器
- `AgentInteractionSteps.vue`
  - 交互卡中的步骤摘要条
- `AgentInteractionDetail.vue`
  - 交互卡中的可展开详细区

### 调整

- `AgentThread.vue`
  - 不再直接遍历平铺 item
  - 改为遍历 `interaction[]`
- 现有 `buildAgentWorkbenchThread(...)`
  - 从返回平铺 `items[]` 改为返回 `interactions[]`

## 数据流

### 输入侧

`useAiAssistantWorkbench.js` 在用户提交时：

1. 创建一个新的 interaction
2. 先将用户消息放入该 interaction
3. 后续根据 dispatch 结果更新这个 interaction：
   - 填入 assistantReply
   - 或持续接入 runtimeCards

### 聊天回答

如果是纯聊天：

- interaction 持有 user message
- `assistantReply` 逐步流式更新
- 最终不生成 runtimeCards

### 执行请求

如果进入 runtime：

- interaction 持有 user message
- 可先有一条短 assistant 摘要
- runtime 事件流持续补充到 `runtimeCards`
- step summary 随之推进

## 错误处理

### 判路失败

如果 dispatch 失败：

- 仍保留本次 interaction
- 在其 `assistantReply` 中直接显示错误
- 状态标记为 `失败`

### 聊天流失败

- interaction 保留
- 失败信息进入助手回复区或错误详情区

### runtime 失败

- interaction 保留
- 状态标记为 `失败`
- 错误详情进入详细步骤区

## 测试策略

### 纯函数测试

新增 view model 变换测试，覆盖：

1. 单次聊天生成单张交互卡
2. 单次执行将 plan / approval / tool / result 收入同一张交互卡
3. 两次用户输入生成两张交互卡
4. 错误事件能正确落到对应交互卡

### 组件结构测试

更新结构测试，确保：

- 线程一级组件不再直接渲染平铺 event card 列表
- 已存在交互卡相关组件

### UI 行为测试

验证：

1. 用户发送一条请求后，线程只新增一张交互卡
2. 该卡内部会随着 runtime 进展逐步更新
3. 下一条用户输入出现时，创建新的交互卡而不是继续往前一张里堆

## 验收标准

满足以下条件即可视为完成：

1. 一条用户输入在主线程中只对应一张交互卡。
2. 该次输入后产生的 assistant 回复、计划、审批、工具调用、结果、错误都归属到同一张卡内部。
3. 用户能在不展开详情的情况下看出每次交互的状态和进展。
4. 详细执行步骤仍然可以展开查看。
5. 线程不再以 plan / approval / tool / result 的散卡形式作为一级视觉结构。
